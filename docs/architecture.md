# Архитектура KnotHop

Дата сверки: 02.11.2026, исходники v0.1.32 (рабочее дерево может содержать более новые незавершённые правки). Экспериментальный пилот, не обещание завершённости всех требований 0013/0014. Утверждения помечены: «по коду» (проверено чтением), «по журналу» (записано в `experiments-log.md`, не перепроверено), «план» (проект, не реализовано).

## Компоненты

`knothopd` — серверный процесс и CLI (`bench/rns-iroh-node/src/vpn.rs`). Android использует тот же Rust-код через JNI (`bench/android/native`) и Java VpnService/UI (`bench/android/vpn`). iroh — 1.3.0 с локальной правкой (`bench/vendor/iroh`, `PATCH.md`): тёплый запасной custom-путь, сторожок застоя пути, фильтр исходящих адресов; в релизе v0.1.32 эти правки отсутствовали (по журналу), форк iroh формально не выбран.

| Плоскость | Что делает | Где |
|---|---|---|
| RNS (форк Leviculum, pin в `deploy/leviculum.ref`) | identity, пути, Link, допуск, управление, T_* | `vpn.rs`, `lib.rs`, `trust.rs` |
| LXMF/PN | зачисление, записи прав, каталог, доставка с удержанием, RRC-хаб | `lxmf_*.rs`, `enroll*.rs`, `rrc.rs` |
| iroh/QUIC | носитель соседей, прямой VPN-канал клиент↔выход, mesh-транспорт | `mux.rs`, `dataplane.rs`, `mesh.rs` |
| TCP-носитель | запасной носитель при блокировке UDP | `tcpc.rs` |

## Пути данных (по коду; раскатано v0.1.31–v0.1.32 по журналу)

Одно QUIC-соединение iroh клиент↔выход несёт два канала, различаемых по первому байту датаграммы ([0023](decisions/0023-direct-first-iroh-data-plane.md)): датаграммы RNS-интерфейса (бит 0x80 первого байта равен нулю), `0xFE` — IP-пакет VPN, `0xFF` — зонд `qprobe`.

```text
1. Прямой путь (0xFE), основной
   TUN → dataplane: [0xFE | IP-пакет] → QUIC-датаграмма соединения носителя клиент↔выход (TLS 1.3, ключ iroh = ключ подписи identity RNS)
       → привязка «ключ iroh ↔ допущенный Link» → on_link_packet(link) → TUN выхода khd0 → NAT → интернет

2. Mesh-транзит (0xFD), когда прямого пути нет
   клиент ⇒ [0xFD | ttl | id(dst) | id(src) | QUIC-пакет сквозного соединения] ⇒ узел T ⇒ … ⇒ выход
   Это обычное сквозное QUIC клиент↔выход (iroh custom transport, mesh.rs); транзитный узел видит только шифротекст и 18-байтный заголовок.
   Далее — как в п. 1 (привязка, on_link_packet).

3. Запасной путь (сейчас)
   TUN → RNS Link datagram (GCM, шифрование между клиентом и выходом) → интерфейс RNS через QUIC-датаграммы или TCP-носитель → 0..N транзитов RNS → Link выхода → on_link_packet
   Применяется, если нет живого QUIC к этому ключу, носитель — TCP, пир не сосед или пакет не помещается в датаграмму (`too_large`).
```

Пакет никогда не отправляется по двум путям сразу; пути без шифрования нет (нет QUIC и нет Link — пакет теряется). Счётчики путей — `dataplane` в `status.json` (`tx`, `rx`, `fallback`, `too_large`, `unbound_drops`), `mesh` (`fwd`, `delivered`, `tx`, `e2e_conns`) — по коду и журналу. Выключатели: `KNOTHOP_DIRECT_DATA`, `KNOTHOP_MESH=0`.

**Привязка и допуск.** Выход привязывает ключ QUIC (`Connection::remote_id()`, доказан TLS, не берётся из содержимого) к Link клиента после допуска (`admit_client13`/`promote_client_link`); клиент привязывает ключ выхода к Link после `T_AUTH_OK` и проверки EXIT. Привязка снимается при закрытии/отзыве Link. Датаграмма без привязки отбрасывается и считается; датаграмма `0xFE` никогда не попадает в RNS. Окончательные проверки (`allowed[link]`, source-IP, per-Link ACL, HOST_ACCESS) остаются в `on_link_packet`/`on_extra_packet` (`lib.rs`) — тот же код, что и для пакетов по Link.

**Mesh-политика (`mesh.rs`, `Trust::mesh_forward_root`).** Узел пересылает кадр только если он не клиент, держит TRANSIT в корне, где предыдущий хоп, src и dst держат права (с учётом отзыва holder/issuer и scope), `ttl>1`, нет разворота, не превышены токен-бакеты на соседа и на пару (src,dst), следующий хоп — сосед с живым QUIC-носителем, датаграмма которого вмещает 1200+18 Б. Следующий хоп: dst-сосед → обратная таблица (src→prev, ≈60 с, учится только от TRANSIT-узла) → путь RNS. Заголовок не аутентифицирован: подмена src может только мешать, сквозной TLS её не примет. Клиент не пересылает. Отзыв в mesh действует с задержкой до 5 с (кэш) — по журналу.

**Носители между соседями.** С ADR [0021](decisions/0021-one-interface-per-peer-carrier-mux.md) у пира один интерфейс RNS (`mux.rs`), QUIC и TCP — носители внутри него: смена носителя не рвёт Link (лаборатория: разрыв 3,7 с при переходе на TCP, 0 потерь при возврате; на пилоте не проверено). После двух неудач или тишины QUIC включается TCP (рукопожатие `RGT3`); возврат на QUIC — через зонд `qprobe` с паузой от 120 с до 30 мин. Память о заблокированных носителях — `health.rs`. Опциональный iroh-relay на порту узла — `relay.rs`; допускает любого держателя прав, проверки TRANSIT в нём нет (по коду, `key_has_rights`).

**Роли RNS/LXMF.** RNS: identity, права, цепочки, поиск пути, Link допуска, управление (`T_*`: T_USE, T_AUTH_OK, T_NBRS, T_OBSERVE и др.), RGP-телеметрия по Link. LXMF: зачисление, записи прав, каталог, доставка через PN, автономное общение нод. Пути RNS служат подсказкой для mesh (следующий хоп), но не полномочием.

**План (не реализовано, [0023](decisions/0023-direct-first-iroh-data-plane.md), [0024](decisions/0024-link-cbc-vanilla-and-thin-fork.md)):** тёплый запасной путь в iroh и реактивное переключение (локальная правка iroh — в работе, в релиз не вошла); телеметрия RGP с Link на QUIC; удаление VPN-пересылки через Link; Link только для управления с штатным AES-256-CBC+HMAC (GCM mode 7 форка и обвязка удаляются), явное назначение Link (`Purpose`) вместо «шифр = роль»; тонкий форк Leviculum. Дополнительно открыто: PMTU (`too_large` ≈3 % на ru1, по журналу), фильтр кандидатов iroh на релизных узлах, TRANSIT-проверка в relay.

Исторические бенчи Channel/Resource не описывают эти пути; Channel — только для управляющих сообщений.

Маршрутизацию и поиск пути выполняет RNS, не телефон как центральный контроллер. При смене пути (не носителя) активный Link может потребовать переустановки; клиентский supervisor выбирает выход и обрабатывает отказ.

## Маршрутизация клиента (`route.rs`)

Настройки — `state/routing.json` (`mode=auto|rules`). Выход задаётся ручным `state/select` или выбирается supervisor по RTT/backoff; старое поле `priority` игнорируется и не ранжирует выходы. Пути по-прежнему строит RNS. В режиме rules клиент решает по dst IP каждого пакета из TUN: подсети из geoip — сразу, домены из geosite и ручные записи — по DNS-ответам, прошедшим через туннель. Порядок совпадения правил независим от выбора выхода: ручные записи выше списков, внутри каждого набора — заданный порядок. Пакет уходит по основному Link, по дополнительному Link к другому выходу или (только подсети) мимо туннеля через `excludeRoute` Android 13+. Недоступный выход правила заменяется основным. Пока есть доменные правила, TCP/UDP на порт 853 отбрасываются (иначе «Частный DNS» скрывает ответы). Исключённых маршрутов не больше 10 000 (предел Binder), мелкие блоки идут через VPN. Файлы списков — недоверенные данные, парсер ограничен по размеру. Подробности и измерения: `experiments-log.md`, W47.

## Identity, корни и права

У каждой ноды собственная identity, создаваемая локально и сохраняемая в `state/identity.key`. Публичная identity и destination hash — разные идентификаторы. Нода всегда корень для самой себя; присоединение добавляет другой якорь, но не передаёт чужому админу её приватный ключ.

| Бит | Право | Смысл |
|---|---|---|
| 1 | USE | пользоваться выходом |
| 2 | TRANSIT | транзитное соседство |
| 4 | EXIT | предоставлять выход при фактически включённом TUN |
| 8 | ADD | выдавать права в пределах своих полномочий |
| 16 | REMOVE | отзывать/понижать права |
| 32 | CONFIG | право настройки; не считать все операции UI/CLI уже реализованными |
| 64 | HOST_ACCESS | exact node-host IPv4 addresses via per-Link TUN ACL; signed node-scoped record, never generic Record v1 |

`trust.rs` проверяет записи с root, holder, issuer, seq, rights и подписью. Проверка идёт цепочкой до локального якоря, с ограниченной глубиной. Нулевые права — отзыв, а не удаление записи. Членство под одним корнем не даёт прав под другим.

HOST_ACCESS хранится отдельно как подписанный `HostAccessRecord` со scope = identity hash target-ноды; root-wide fallback запрещён. Network delegate может администрировать HOST_ACCESS только если root подписал ему scoped HostAccessRecord для той же target-ноды и у делегата отдельно есть ADD/REMOVE в том же принятом root. Generic Record v1 не несёт scope и отвергает bit 64. Direct LXMF управляет статусом и этой записью; полученная Link identity или destination/address hint сама по себе не даёт полномочий.

Набор nft по IP (`host_access_v4` + `host_access_dest_v4`, INPUT на `khd0`) — **вторая линия защиты** для HOST_ACCESS TCP, не источник решения. Решает Rust до записи в TUN: `allowed[link]==src` и per-Link бит `host_access` (`on_link_packet`); worker только публикует адреса уже допущенных Link с лизингом ядра 3 с, поэтому падение worker и reload nftables закрывают доступ, а не открывают. Инвариант: единственный писатель клиентских пакетов в TUN выхода — `on_link_packet`/`on_extra_packet` клиентского `ClientCtx`; если появится путь записи в TUN в обход него, адресный набор уже не защитит, и такой путь нужно закрывать так же per-Link проверкой. Коллизия 17-битного `client_ip` не даёт доступа: у адреса не бывает двух допущенных Link (`address clash`), а Link другой identity не наследует `host_access`. Порты не ограничены (модели портов в host-acl нет): держатель получает все TCP-порты на разрешённых адресах ноды.

Допуск соседа требует общего корня с TRANSIT у обеих сторон; допуск VPN-клиента — EXIT у сервера и USE у клиента. Клиент проверяет EXIT сервера, не только факт AUTH_OK. Identity подтверждается механизмом Link identify; адрес и тег этого не заменяют.

Права не равны назначению конкретного соединения. `T_USE` обозначает VPN-клиента, `enroll_only` — временный Link зачисления; `lc:false` в анонсе — отказ от планирования входящего mesh-Link. Эти признаки не выдают прав. Телефон пилота не становится транзитом только потому, что он собственный админ.

## Приглашение и зачисление

Приглашение v4 — строка `kh-<base64url>` (QR несёт `knothop://i/<тот же хвост>`), решение [0019](decisions/0019-invite-v4-adminless-enrollment.md): хеши 1–8 выбранных нод по возрастанию, **секретный одноразовый pin 24 Б**, контрольная сумма 4 Б. Корня, прав и срока в строке нет; адресов тоже нет, путь к нодам строит RNS. Это bearer-секрет целиком; контрольная сумма — не подпись и не защита от кражи. Приватного ключа в приглашении нет. Форматы v1–v3 и `kh2-`/`kh3-` удалены.

Срок — 48 часов. Каждая выбранная нода сама проверяет pin и подписанный Grant (корень, права ⊆ USE|TRANSIT|EXIT, срок, список нод), поэтому зачисление не зависит от онлайна админа. Fail2ban на ноде: неверный pin даёт задержку min(60 с, 0,5 с × k²). После погашения pin закрывается durable и сообщается остальным нодам по LXMF (`enroll/4`, с доставкой через PN); повтор тем же holder возвращает тот же результат, другой holder права не получает.

Путь (в коде `enroll.rs`, `enroll_net.rs`; RNS Request `/enroll/v4`):

1. Новичок открывает Link к нодам приглашения (порядок случайный) и шлёт LOOKUP с pin.
2. Нода отвечает подписанным предложением: корень, пригласивший, права, срок, цепочка. Новичок проверяет подписи и соответствие pin/нодам.
3. Приложение показывает диалог согласия (корень, пригласивший, права, срок). Без согласия pin не гасится.
4. REDEEM: подпись согласия новичка над Grant; нода выдаёт scoped-запись (права действуют только на выбранных нодах, без делегирования; отзыв корня доминирует), закрывает pin и отвечает выпустившему по LXMF.

Администратор приглашения выбирает ноды и маску прав. По уточнению [0020](decisions/0020-async-invites-lxmf-delivery.md) (27.10, локально, ещё не на пилоте) QR появляется после сохранения подписанного разрешения в приватной очереди админа; ISSUE/issued доставляются асинхронно через LXMF direct/PN. На каждой выбранной ноде по-прежнему должен быть якорь корня администратора — первая выдача на ноду без якоря не реализована. Отсутствие разрешения до доставки больше не является окончательным отказом новичку. Pin для ещё не ответивших нод временно хранится в приватной очереди клиента; фоновая выдача допускается только с прежним явным согласием на тот же Grant. Репликация на два PN не реализована.

После зачисления новичок получает записи и приватный каталог по LXMF — подсказку адресов, а не полномочие. `T_NBRS` сообщает клиенту о связях выхода для графа, не авторизует выходы и не является центральной таблицей маршрутов.

С 28.10 каталог обновляется отдельно от расписок приглашения: `trust.sync/1` с `get_dir:true` запрашивает его у известного авторизованного выхода. Ответ содержит адреса/identity нод общей сети; отдельными подписанными записями передаются видимые адресату цепочки EXIT. Проверяется членство адресата именно в соответствующем root и scope этой ноды, перед каждой отправкой/повтором членство проверяется заново. Чужие root и обычные USE-only пользователи в каталог не попадают. Один ответ в минуту на identity, не более 16 записей; клиент опрашивает максимум два выхода раз в 120 с и при потягивании страницы вниз. Допущенному VPN-клиенту каталог также отправляется при подключении и раз в 5 минут. Истечение/полнота приглашения не отключает каталог. Адреса не дают USE на другой scope: право на выход по-прежнему требует EnRec или отдельной подписанной выдачи.

Опрос недостающих расписок независим: сначала известные комиссионеры (до двух за проход, с вращением), затем отсутствующие ноды. Рабочий Link клиента переиспользуется без закрытия после RPC; для нового поиска пути установлен предел 20 с, для всего фонового прохода — 120 с. Каталог и его UI-индикатор не блокируются этим проходом. В публичной RNS период анонса по-прежнему 600 с; поиск маршрутов остаётся задачей RNS, каталог даёт лишь identity/адресные подсказки.

Делегированное приглашение v3 ([0017](decisions/0017-delegated-invites.md)) заменено v4: scoped-запись выдаёт сама нода по подписанному Grant.

## PN-хранилище (встроенный propagation node)

- Серверные ноды держат штатный LXMF PN (`lxmf_sync::propagation_processor`), хранилище — `state/lxmf/propagation/` (`FilePropagationStore`, файл на сообщение), потолок задаёт `PnLimits::auto`: `pn_cap_mb` из node.json (1…4096 МиБ), иначе 1% свободного места каталога состояния в пределах 2…100 МиБ (`PN_CAP_BYTES`…`PN_CAP_AUTO_MAX`; до W110 было 8 МиБ, до W133 всегда 2 МиБ). Узлам с малым диском (uae, by) достаётся малый буфер без отдельной настройки. PN — буфер доставки и реплика между нодами, а не источник прав: права живут в `trust.json`/Store зачисления, proof пересылаются при подключении пира, закрытия восстанавливает `recover`. Потеря содержимого PN не меняет права и не ломает приглашения; при переполнении движок вытесняет старое (`make_room`).
- `FilePropagationStore::open` читает **каждый** файл (stat + 16 байт), на вращающемся диске ≈165 файл/с. Поэтому PN строится в фоне: `core_processor(...)` возвращается сразу, поток `lxmf-pn-load` сначала удаляет по именам (без чтения) просроченные (>48 ч) и всё сверх `max_files` (8192 при 2 МиБ, до 65 536 при большом потолке), затем открывает хранилище, вытесняет самые старые до потолка и отдаёт движок через канал. Горячий путь процессора — только `try_recv`; пока PN не готов, его события и тики пропускаются (LXMF-админка и приглашения используют PN-клиент и свой router, а не этот движок). Ошибка открытия не останавливает узел: PN остаётся `failed`.
- Состояние видно в `status.json` → `pol.pn_state` (`off|loading|ready|failed`), `pn_ready`, `pn_load_ms`, `pn_trimmed`, `pn_files`, `pn_bytes`, `pn_cap_bytes`. Пока `pn_ready=false`, удалённые PN-пиры к этому узлу не достучатся.
- **Устойчивость доставки через PN (W133).** Отправитель не может спросить чужой PN, хранит ли он письмо (в LXMF нет такого запроса для не-адресата), поэтому вытеснение или потеря на PN определяются только по отсутствию прикладного ACK адресата. `lxmf_admin::sync_tick`: прямая доставка повторяется до ACK/`exp`; через 30 с без ACK ставится копия на PN. Исход копии берётся из событий роутера: `AwaitingCollection` — PN принял, `Failed`/`Rejected` или копия в очереди дольше 180 с — PN в выдержку (`PnHealth`: 60, 120, … до 1800 с), `pn_tick` переключает исходящий PN на лучший без выдержки (услышанный анонс, меньше хопов). Принятая, но не подтверждённая копия через интервал 60→1800 с повторяется через другой PN, всего до 32 копий (≈10 ч), дальше остаётся прямая доставка. Один PN: после выдержки используется снова. Ограничение: исходящий PN у роутера один, поэтому выборка почты идёт только с текущего PN; доставка между PN опирается на пиринг серверов.

## RRC-хаб (Reticulum Relay Chat)

- Серверные ноды держат хаб RRC 0.1.3 ([rrc.kc1awv.net](https://rrc.kc1awv.net)): `rrc.rs`, `HubProcessor` рядом с процессорами админки и PN. Назначение `rrc.hub` (identity ноды) анонсируется в RNS с **пустым app_data** первый раз через 25 с после старта, далее раз в 600 с. В анонсе нет адресов, имён сети и меток VPN (AGENTS.md, п. 9). На телефоне хаба нет.
- Решение владельца 29.10: Link принимается от любой identity публичной RNS. Поэтому всё от клиента недоверенно. Конверт — CBOR-карта с числовыми ключами, разбирается собственным минимальным кодеком (глубина ≤8, без неопределённой длины, повтор ключа 0…7 и неверная версия — отказ, неизвестные ключи пропускаются); тело (ключ 6) непрозрачно и пересылается байт в байт. Данные идут обычными пакетами Link (`send_packet_on_link`, контекст None), а не Channel; без `T_*` и VPN-допуска.
- Хаб не хранит сообщения и не федерируется: комната существует, пока в ней есть участники. MSG/ACTION уходит всем участникам комнаты **включая отправителя** (как в rrcd: клиенты, например rrc-tui, принимают собственное эхо за подтверждение доставки и без него через 30 с помечают сообщение недоставленным); поле 4 (sender) обязано совпадать с identity Link. JOINED (себе) несёт до 12 identity участников, остальным участникам при входе/выходе уходят JOINED/PARTED с `[identity]`, как в rrcd; PARTED выходящему — тоже список `[identity]`; PONG повторяет тело PING. WELCOME — карта с числовыми ключами как у rrcd: 0 имя (`rrc_name`, по умолчанию «hub»), 1 версия, 2 возможности (`{1: true}` — ACTION), 3 пределы (ключи 0…4: ник, комната, тело, комнат на сессию, сообщений в минуту); текстовые ключи клиенты не читают. NOTICE от клиентов (в т. ч. прямые, K_DST=8), ресурсы (тип 50) и модерация rrcd (режимы комнат, регистрация) не поддерживаются.
- Пределы: 48 сессий (при заполнении вытесняется сессия без комнат, молчащая >10 мин, иначе новый Link закрывается), ≤4 сессии на identity, ≤8 комнат на сессию, ≤128 комнат всего, комната ≤64 Б (нижний регистр, без управляющих), ник ≤32 Б, тело ≤354 Б, пакет ≤500 Б. Ведра: пакеты 20 (2/с), MSG 30/мин (burst 10), JOIN/PART 10/мин (burst 6), PING 20/мин (burst 10, лишнее молча отбрасывается: rrc-tui пингует раз в 5 с), общий fanout 10/с (burst 20); 6 нарушений за 60 с — ERROR и закрытие. Рукопожатие (HELLO + LinkIdentified) — в течение 30 с; до WELCOME обслуживается только HELLO. Молчащая сессия получает PING раз в 10 мин, без единого пакета 60 мин — закрывается.
- Link хаба не входят в VPN-таблицу `links`: `node_events` пропускает `LinkDataReceived` на них (`rrc::is_hub_link`), VPN-соседей хаб не вытесняет.
- Настройка: `node.json` → `"rrc": false` отключает хаб, `"rrc_name"` задаёт имя. Состояние — `status.json` → `pol.rrc_on`, `rrc_sessions`, `rrc_rooms`, `rrc_msgs`, `rrc_dropped`, `rrc_refused`, `rrc_announces`.
- Ограничения: слоты сессий могут занять атакующие (identity дешёвая; смягчено вытеснением, лимитом на identity и idle-закрытием); fanout выполняется под блокировкой ядра; каждый `send_packet_on_link` заводит raw-receipt (объём ограничен rate-limit); число Link ядра (`max_links`) в knothopd не задано. Интероп проверен локально с клиентом rrc-tui на Python RNS 1.5.7 и сверен с rrcd (W134); с Nomad Network, MeshChatX и другими клиентами не проверялся.

## Адреса и наблюдаемость

- Identity не зависит от IP. Адреса приходят из конфигурации, DNS, анонсов и каталога; принимаются только как hints.
- Диалеры читают обновляемую книгу адресов. DNS переразрешается при попытке, автоматические локальные адреса нода пересматривает раз в 60 с. Явный `advertise` сам по себе не обновляет публичный IP за NAT.
- `vis=direct` — RNS-путь через прямой интерфейс к узлу; `via` — через другой узел; `none` — пути нет. `nh` показывает первый транзит, если он определён. Это наблюдение состояния пути, не доказательство способности передать 100 МБ.
- `lk`/`why` — состояние/отказ Link; `q` — счётчики контактов и смен пути. Статистика не подменяет маршрутизацию RNS.
- Рёбра из `T_NBRS` — ограниченный, устаревающий снимок, полученный от выхода; полной мгновенной карты всей сети нет.

## Границы безопасности

Публичные RNS-узлы используются для обнаружения. Данные VPN и pairing идут по нашим транспортным интерфейсам. Анонсы, DNS и каталоги могут быть вредоносными; сетевые адреса фильтруются, а допуск проверяется отдельно на конечном Link.

Оператор выхода видит трафик, не защищённый протоколом приложения, например незашифрованный HTTP. Сквозной Link не защищает от самого выхода. Постоянная identity позволяет сопоставлять участника; сокрытие членства не гарантируется.

Пилот использует локальный форк Leviculum, в том числе криптографические/производительные изменения. Сборка с upstream без patch не эквивалентна пилоту. Внешнего криптографического аудита нет, активный rekey не завершён.

Подробные фактические проверки — W40–W42 журнала. Приоритеты ревью: авторизация и отзыв, pairing и одноразовость, защита до допуска, DoS/SSRF, Android boundaries, деплой и зависимости.
