# Архитектура rawg

Дата сверки: 19.10.2026, исходники волны 6. Экспериментальный пилот, не обещание завершённости всех требований 0013/0014.

## Компоненты и путь данных

`rawgd` — серверный процесс и CLI в `bench/rns-iroh-node/src/vpn.rs`. Android использует тот же Rust-код через JNI (`bench/android/native`) и Java VpnService/UI (`bench/android/vpn`).

```text
IP-пакет из TUN
  → RNS Link datagram (шифрование между клиентом и выходом)
  → интерфейс RNS поверх iroh/QUIC datagrams либо TCP-носителя
  → ноль или несколько транзитов RNS
  → RNS Link выхода → серверный TUN rgd0 → NAT → интернет
```

Управляющие сообщения идут по Channel; VPN-пакеты и данные бенча — ненадёжными Link datagrams. Потери не скрываются собственной надёжной передачей IP-пакетов. Исследовательские stream/Resource-бенчи не описывают этот путь.

QUIC — предпочтительный носитель между соседями. После двух неудач подключения включается TCP. Попытки возврата на QUIC начинаются через 120 с; пауза растёт до 30 мин. TCP-носитель не отменяет шифрование RNS. Нет iroh-relay: ретранслятор — наш RNS-узел с TRANSIT.

Маршрутизацию и поиск пути выполняет RNS, не телефон как центральный контроллер. При смене пути активный Link может потребовать переустановки; клиентский supervisor выбирает выход и обрабатывает отказ.

## Маршрутизация клиента (`route.rs`)

Настройки — `state/routing.json` (режимы auto | priority | rules). Приоритеты только переупорядочивают кандидатов supervisor; пути по-прежнему строит RNS. В режиме rules клиент решает по dst IP каждого пакета из TUN: подсети из geoip — сразу, домены из geosite и ручные записи — по DNS-ответам, прошедшим через туннель. Пакет уходит по основному Link, по дополнительному Link к другому выходу или (только подсети) мимо туннеля через `excludeRoute` Android 13+. Недоступный выход правила заменяется основным. Пока есть доменные правила, TCP/UDP на порт 853 отбрасываются (иначе «Частный DNS» скрывает ответы). Исключённых маршрутов не больше 10 000 (предел Binder), мелкие блоки идут через VPN. Файлы списков — недоверенные данные, парсер ограничен по размеру. Подробности и измерения: `experiments-log.md`, W47.

## Identity, корни и права

У каждой ноды собственная identity, создаваемая локально и сохраняемая в `state/identity.key`. Публичная identity и destination hash — разные идентификаторы. Нода всегда корень для самой себя; присоединение добавляет другой якорь, но не передаёт чужому админу её приватный ключ.

| Бит | Право | Смысл |
|---|---|---|
| 1 | USE | пользоваться выходом |
| 2 | TRANSIT | транзитное соседство |
| 4 | EXIT | предоставлять выход при фактически включённом TUN |
| 8 | ADD | выдавать права в пределах своих полномочий |
| 16 | REMOVE | отзывать/понижать права |
| 32 | CONFIG | право настройки; не считать все операции UI/CLI уже реализованными |

`trust.rs` проверяет записи с root, holder, issuer, seq, rights и подписью. Проверка идёт цепочкой до локального якоря, с ограниченной глубиной. Нулевые права — отзыв, а не удаление записи. Членство под одним корнем не даёт прав под другим.

Допуск соседа требует общего корня с TRANSIT у обеих сторон; допуск VPN-клиента — EXIT у сервера и USE у клиента. Клиент проверяет EXIT сервера, не только факт AUTH_OK. Identity подтверждается механизмом Link identify; адрес и тег этого не заменяют.

Права не равны назначению конкретного соединения. `T_USE` обозначает VPN-клиента, `enroll_only` — временный Link зачисления; `lc:false` в анонсе — отказ от планирования входящего mesh-Link. Эти признаки не выдают прав. Телефон пилота не становится транзитом только потому, что он собственный админ.

## Приглашение и зачисление

Приглашение `rawgi-…` (либо его представление эмодзи/QR) содержит публичный ключ пригласившего, **секретный одноразовый pin**, права, время и подсказки обнаружения; формат v3 описан в [0017](decisions/0017-delegated-invites.md). Это bearer-секрет целиком; контрольная сумма — не подпись и не защита от кражи. Клиентский приватный ключ в новом приглашении отсутствует.

Pin хранит и погашает выпустивший его админ. Срок — 30 дней. Повтор тем же holder нужен для восстановления потерянного ответа; другой holder не должен получить права после погашения. После зачисления приглашение игнорируется, работа идёт по сохранённым ключам и записям.

Пути зачисления:

1. При доступном адресе админа — Link к нему и `T_PAIR1`.
2. Телефон может услышать анонс ждущей ноды и сам открыть временный Link к ней.
3. При недоступности прямого пути новичок — и `node`, и `client` — просится через ноду-посредника (`T_PAIRQ`). Mesh доставляет запрос админу; админ проверяет MAC от pin и подписывает запись о новом holder. Сам pin по сети не передаётся.

Анонс админа сообщает, что он онлайн; без него у node есть редкая запасная попытка. Новое зачисление зависит от доступности админа, а уже зачисленные ноды продолжают работать по сохранённым записям. Приглашение ограничивает входные ноды для зачисления, **не** устанавливает пер-нодовый scope выданных прав.

Делегированное приглашение: участник D с ADD в сети корня R зачисляет новичка в сеть R, а не в своё дерево — пройдя проверку цепочки R→…→D→N в `trust.rs`, новичок делает якорем корень R (формат v3, MAC с корнем, pin хранит корень; [0017](decisions/0017-delegated-invites.md)). В `trust.rs` реализовано; сетевой обмен в `vpn.rs` — на внедрении, до этого новичок по-прежнему якорится на пригласившего.

После pairing новичок получает записи и `T_DIR` — каталог адресов/ключей/имён. Это помогает не ждать следующего анонса; каталог остаётся недоверенной подсказкой. `T_NBRS` сообщает клиенту о связях выхода для графа, не авторизует выходы и не является центральной таблицей маршрутов.

Текущая UI-генерация приглашения локальная. Исходный замысел «опросить все выбранные ноды и собрать один ключ из ответов» не реализован; ожидание админа и срок 30 дней сами по себе этого не заменяют.

## Адреса и наблюдаемость

- Identity не зависит от IP. Адреса приходят из конфигурации, DNS, анонсов и каталога; принимаются только как hints.
- Диалеры читают обновляемую книгу адресов. DNS переразрешается при попытке, автоматические локальные адреса нода пересматривает раз в 60 с. Явный `advertise` сам по себе не обновляет публичный IP за NAT.
- `vis=direct` — RNS-путь через прямой интерфейс к узлу; `via` — через другой узел; `none` — пути нет. `nh` показывает первый транзит, если он определён. Это наблюдение состояния пути, не доказательство способности передать 100 МБ.
- `lk`/`why` — состояние/отказ Link; `q` — счётчики контактов и смен пути. Статистика не подменяет маршрутизацию RNS.
- Рёбра из `T_NBRS` — ограниченный, устаревающий снимок, полученный от выхода; полной мгновенной карты всей сети нет.

## Границы безопасности

Публичные RNS-узлы используются для обнаружения. Данные VPN и pairing идут по нашим транспортным интерфейсам. Анонсы, DNS и каталоги могут быть вредоносными; сетевые адреса фильтруются, а допуск проверяется отдельно на конечном Link.

Оператор выхода видит трафик, не защищённый протоколом приложения, например незашифрованный HTTP. Сквозной Link не защищает от самого выхода. Постоянная identity позволяет сопоставлять участника; сокрытие членства не гарантируется.

Пилот использует локальный форк Leviculum, в том числе криптографические/производительные изменения. Сборка с upstream без patch не эквивалентна пилоту. Внешнего криптографического аудита нет, активный rekey не завершён.

Подробные фактические проверки — W40–W42 журнала. Приоритеты ревью: авторизация и отзыв, pairing и одноразовость, защита до допуска, DoS/SSRF, Android boundaries, деплой и зависимости.
