# Исторические измерения (не текущая спецификация): Python RNS 1.5.7 в Docker

Сырые данные: `bench/results/raw/` (JSON и логи каждого прогона), методика и ограничения - [bench/README.md](../bench/README.md). Таблицы ниже сгенерированы `bench/aggregate.py` из сырых JSON.

**Что измерено:** RNS Link / Resource между контейнерами в локальных docker-сетях, Python RNS 1.5.7, интерфейсы TCP, Backbone, UDP, 0/1/2 транспортных узла, потери 0 и 1% (netem на исходящем трафике клиента). По 3 повтора на ячейку.

**Чего здесь нет:** QUIC/iroh, leviculum как конечная точка (как транспорт измерен, см. раздел ниже), публичная сеть RNS, NAT, реальные задержки, несколько одновременных потоков, Android, цель 2 (синхронизация реестра, живость). Поэтому цели 2 и 3 плана **не закрыты**: закрыт только первый шаг цели 3 для Python RNS.

**Условия:** хост общий (Docker-контейнеры других проектов, load average около 4 на 12 ядер), каждый контейнер закреплён на своём ядре, ядро 7.2.6-zen2. Цифры отражают этот стенд, не «Reticulum вообще».

## Что показывают данные

Каждый пункт помечен уровнем уверенности. «Наблюдение» - прямо следует из таблиц; «гипотеза» - объяснение, которое стенд не проверял.

1. **Потолок Python RNS на TCP/Backbone около 25-28 МиБ/с (210-240 Мбит/с) без транспортных узлов** при загрузке 77-78% ядра на обоих концах. Причина разобрана отдельно в разделе «Почему так медленно» ниже: это стоимость криптографии и хеширования на байт в одном конвейере, а не сеть и (вопреки первой версии этого отчёта) не GIL.
2. **Размер MTU решает больше, чем выбор транспорта.** TCP при `fixed_mtu = 500`: 4,8 МиБ/с и полный overhead 1,246, против 25,1 МиБ/с и 1,016 при автонастройке (16384). Рост в 5,3 раза и сокращение overhead с 24,6% до 1,6%. *Наблюдение.*
3. **UDP при MTU 500 медленнее TCP при том же MTU** (1,77 против 4,76 МиБ/с), хотя overhead у UDP ниже (1,158 против 1,246). *Наблюдение;* причину (покадровая обработка, отсутствие потокового режима) стенд не выяснял.
4. **Каждый транспортный узел снижает goodput:** TCP 25,1 -> 21,9 -> 20,9; Backbone 28,5 -> 22,1 -> 18,3; UDP 1,77 -> 1,40 -> 1,19 МиБ/с (0 -> 1 -> 2). Для TCP разброс между повторами перекрывается (21,1..25,6 при одном узле), поэтому уверенно можно говорить о тенденции, не о точном проценте. Overhead от числа узлов на клиентском звене не меняется (измерялось только первое звено).
5. **Задержка мала и растёт с узлами:** эхо-запрос 32 Б, TCP: p50 0,74 -> 1,13 -> 1,18 мс, p95 1,07 -> 2,78 -> 3,01 мс; UDP: p50 1,32 -> 1,86 -> 3,24 мс. На локальном мосту без NAT; для реальных сетей не переносится.
6. **Overhead на данных у TCP/Backbone с автонастройкой MTU около 1,5-1,6%** (RNS 1,0%, L2-L4 0,5-0,6%). У UDP при MTU 500 - 15,8%. *Оговорка:* см. п.4 ограничений в bench/README (GSO).
7. **Простой (один установленный link, без анонсов в окне):** RNS-уровень 8,4 Б/с напрямую и около 26,7 Б/с через транспортные узлы; на проводе по портам стенда (TCP/Backbone) 48 Б/с (0,6 пакета/с) напрямую и около 80 Б/с (0,8 пакета/с) через транспортные узлы; у UDP 25 и 41 Б/с. Это стоимость keepalive и подтверждений **одного** link; стоимость анонсов и синхронизации реестра (цель 2) здесь не измерена.
8. **Потери 1% на исходящем трафике клиента, один транспортный узел:** TCP почти не страдает (19,9 против 21,9 МиБ/с, overhead без изменений), UDP падает в 14 раз (1,40 -> 0,10 МиБ/с), при этом CPU около 5%: передача ждёт таймеров повторной отправки Resource. *Наблюдение.* *Оговорка:* TCP устойчив здесь в основном потому, что RTT около 1 мс и повторная отправка мгновенна; на длинных каналах результат будет другим. Потерянные netem'ом пакеты в счётчик tx не попадают, поэтому overhead при потерях слегка занижен.
9. **Обнаружение пути - важная находка для проекта.** По умолчанию (режим интерфейса `full`) транспортный узел **не пересылает запрос о неизвестном пути**: путь появился только вместе с очередным анонсом сервера (19,3-19,5 с при периоде 20 с; 59,4 с при периоде 60 с). С `mode = gateway` на интерфейсах транспортных узлов путь находится за 0,05 с. Причина в коде: `RNS/Transport.py:3430`, пересылка только для режимов `access_point`, `gateway`, `roaming` (`Interface.py:55`). *Наблюдение + исходный код.* Следствия для проекта - в [архивном плане](archive/plan.md), раздел 4.1.
10. **`fixed_mtu` Backbone не поддерживает** (link MTU остался 32768 в «aligned»): строки `backbone aligned` в таблице не выровнены и сравнению с TCP aligned не подлежат; фактически это тот же Backbone с автонастройкой MTU. Числа ниже, чем у `backbone default` (25,3 против 28,5 МиБ/с; диапазоны повторов не перекрываются), вероятно из-за короткой передачи 8 МиБ вместо 128 (влияние старта) - не проверено.

## Почему так медленно для локального канала

Вопрос владельца: сам канал между контейнерами даёт десятки Гбит/с, а RNS выжимает 0,2. Первая версия этого отчёта объясняла это упором Python в один поток (GIL) и **не проверяла**. Проверка показала, что объяснение было неверным. Данные: `bench/results/profiles/`, `bench/results/raw/cores*`, `par*`; скрипты `bench/Dockerfile.prof`, `bench/crypto_bench.py`, `bench/profile_summary.py`.

| Проверка | Результат | Вывод |
|---|---|---|
| Сырой TCP между двумя контейнерами через тот же docker bridge (iperf3, 1 поток) | 30,8 Гбит/с; 13,5 Гбит/с блоками по 16 КБ | Канал не причина: RNS в 150 раз ниже потолка среды |
| Скорость примитивов RNS на этом CPU (Token = AES-256-CBC + HMAC-SHA256, провайдер `cryptography`) | шифрование 133-136 МиБ/с, расшифровка 144-157 МиБ/с (блоки 16 КБ и больше); SHA-256 271 МиБ/с; на пакетах 400 Б всего 14 МиБ/с | Крипто не «бесплатно». У CPU (i7-8750H) есть AES-NI, **нет SHA-NI** (по `/proc/cpuinfo`) |
| py-spy `--gil`, 5 с во время передачи 512 МиБ | GIL занят 16% времени на клиенте и 16% на сервере | Python-код и GIL не узкое место |
| py-spy без `--gil` (учитывает вызовы OpenSSL без GIL) | клиент: SHA-256 около 33% времени, шифрование около 5%, подготовка следующего сегмента (`Resource.__prepare_next_segment`) 48%; сервер: SHA-256 около 23%, чтение сокета 14%, расшифровка и проверка HMAC около 10% | Основное время идёт в хешировании и шифровании: каждый пакет хешируется для идентификатора, хеша части и проверки целостности, и всё это дважды (отправитель и получатель) |
| Число ядер на контейнер при одном Resource (1 / 2 / 4 ядра) | 25,2 и 23,5 / 24,4 и 23,1 / 24,7 и 21,5 МиБ/с; загрузка 77-86% ядра | Дополнительные ядра не помогают: **один Resource - один последовательный конвейер**, он использует около 0,8 ядра |
| Несколько Resource по независимым link одновременно, 1 ядро на контейнер | 1 link 26,0; 2 link 25,9; 4 link 24,0 МиБ/с | На одном ядре потолок один и тот же: упор в процессор |
| То же, 4 ядра на контейнер | 1 link 25,4; 2 link 34,4; 4 link 41,1 МиБ/с (загрузка 1,5 и 1,9 ядра) | Параллельные link масштабируются, но **сублинейно** (в 1,6 раза на 4 link) |

**Вывод (подтверждён измерениями):**
1. Скорость ограничена процессором, а не сетью: на каждый переданный мегабайт RNS тратит около 30 мс процессорного времени на каждой стороне (0,8 ядра при 25 МиБ/с), то есть около 32 МиБ/с на ядро как потолок для одного конвейера.
2. Один Resource не может использовать больше одного ядра. Для нескольких одновременных потоков (а именно так устроен `resilum-core`: отдельный link на TCP-поток) суммарная скорость растёт с числом link до 41 МиБ/с на 4 ядрах в этом тесте.
3. Рост не линейный; что именно его ограничивает (части кода под GIL, общий путь транспортного узла, синхронизация), стенд не выяснял.

**Не доказано:** точное распределение времени между этапами (профиль показывает доли в выборке, а не причинность); влияние SHA-NI (на CPU с аппаратным SHA-256 хеширование должно дешеветь, но здесь это не проверялось); поведение leviculum (Rust) - возможно, быстрее, но это нужно мерить. Цифры относятся к ноутбучному процессору 2,2 ГГц на загруженном хосте.

Что видно (наблюдения):
1. **При большом MTU (TCP и Backbone, 16-32 КБ) с `lnsd` в середине цепочки скорость ниже на 26-45%** (медианы; диапазоны повторов Python и `lnsd` не пересекаются). Закономерности по числу узлов нет (у TCP хуже на двух узлах, у Backbone на одном). **При MTU 500 и у UDP разница разнонаправленная (от -11% до +21%) и в пределах разброса** - вывода не делаю; там скорость определяется малым размером пакета, а не реализацией транспорта.
2. **Процессор транспортного узла не объясняет разницу:** он загружен примерно одинаково у обеих реализаций (около 30-35% ядра), концы цепочки с `lnsd` загружены даже меньше. Значит, концы чего-то ждут, а не работают на пределе.
3. **Причина не установлена.** Моя попытка сравнить размеры TCP-сегментов на транспортном узле дала некорректный разбор (захват с GSO), результат отброшен. Гипотезы (дополнительная задержка пересылки на узле, иная буферизация записи в сокет, иная реакция на окно Resource) не проверялись.
4. **Backbone в `lnsd`** обрабатывается как обычный TCP-интерфейс (в логах `tcp_server/...`), `BackboneInterface` как отдельный тип не реализован, поэтому строки `backbone` сравнимы с TCP, но не доказывают ускорения epoll-реализации.

| 2 | gateway | 0.05, 0.05 |
| 2 | full | 18.41, 18.72 |

**Ограничения этого сравнения:** `lnsd` измерен только как транспорт, а не как конечная точка (клиент и сервер на Rust не запускались: скрипт замера работает на Python RNS); версия `lnsd` - nightly, не релиз; то, что `lnsd` медленнее в роли транспорта, не говорит о его скорости как конечной точки.

## Ограничения этих чисел

**Продолжение:** [Backbone поверх AmneziaWG 3.1](benchmarks-awg.md) — отдельная серия из пяти повторов с настройкой MTU и параллельных Link. Найден агрегатный режим быстрее прежней конфигурации; прежние значения здесь сохраняются как результаты предыдущего этапа, не абсолютный потолок RNS.

- Три повтора; для IQR нужно четыре и больше.
- Размеры передач различаются между ячейками (128 МиБ для автонастройки MTU, 8 МиБ для MTU 500 и UDP): короткие передачи сильнее подвержены влиянию старта.
- Измерено только первое звено цепочки; узкое место на дальних звеньях видно лишь по CPU.
- Фоновая нагрузка хоста не контролировалась.
- Шифрование RNS и издержки Python не разделены.

## Следующие шаги

1. Измерить leviculum как конечную точку (клиент и сервер на Rust, например через `lncp`/`lnstest`): как транспорт он измерен, но скорость конечной точки неизвестна. Выяснить причину замедления `lnsd` в роли транспорта.
2. Добавить QUIC: community-интерфейс `kageedwards/reticulum-quic-interface` для Python RNS (исследовательский, 0 звёзд, без тестов) и отдельно iroh в `resilum-core` после правки его резолверов (см. review-2, п.10).
3. Измерить цель 2: накладные расходы анонсов и синхронизации реестра при N = 5..100 узлах, время выпадения мёртвого узла.
4. Повторить на машине с аппаратным SHA-256 (SHA-NI) и на leviculum, чтобы отделить стоимость протокола от стоимости реализации.
5. Прогон на двух хостах и с задержкой/потерями netem на обоих направлениях.
