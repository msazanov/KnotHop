# Предложение: администрирование других нод в Android UI

Дата: 2026-10-23. Статус: **предложение**, не решение владельца. Автор: субагент UX/mapping.
Область: только Android UI и его связка с `status.json`/нативной частью. Логику протокола и права описывает отдельное предложение logic-агента: `docs/proposals/remote-node-administration-logic-2026-10-23.md` (на момент написания может ещё отсутствовать; здесь на него только ссылка по смыслу, анализ не дублируется). При расхождении приоритет у logic-документа и ADR.

**Статус фактов о backend: «по коду Android/ADR, требуется сверка с backend».** Утверждения «backend нет/не реализован» ниже выведены из Android-кода и ADR 0013/0015/0018/0019 и из того, что не нашёлся модуль удалённого администрирования при поиске по репозиторию. Rust-часть (`bench/rns-iroh-node/src`) целиком не читалась, поэтому «нет» здесь — не доказанный факт, а рабочая гипотеза для сверки. Метка **[нет backend]** читается как «в Android/ADR не обнаружено, сверить».

## 0. Как читать

Каждый пункт помечен одной из меток:

- **[есть]** — работает в коде сейчас (прочитано в `bench/android/vpn/`, ADR 0013/0015/0018/0019).
- **[предложение]** — UI-решение этого документа, на существующих примитивах.
- **[нет backend]** — нужен backend, которого пока нет (LXMF в knothopd, Invite v4, scope, `ENROLL_*`, HOST_ACCESS, удалённые команды к чужой ноде, журнал действий, подписки на события).

Не принято и не предполагается принятым:

- ограничение «ADD + приглашение» (0019 §16, открытый вопрос владельцу);
- конкретная позиция бита HOST_ACCESS (называем «будущий бит»);
- любая биометрия/`ADMIN_CONFIRM` под другим именем (убрана владельцем, 0019).

Вне MVP и вне этого предложения: shell, reboot, правка firewall, systemd, произвольные команды на ноде. Своего общего shell-протокола нет и не планируется.

## 1. Принципы

1. **Один главный путь остаётся быстрым.** Открыл приложение → тап по ноде → выход выбран → подключено. Админ-функции не добавляют шагов на этот путь.
2. **Администрирование — отдельный осознанный вход**, не короткий тап.
3. **Только реальные примитивы:** просмотр статуса/участников, выдача/отзыв USE/TRANSIT/EXIT (и позже HOST_ACCESS), приглашения, отзыв холдера. Остальное UI не показывает даже как неактивное.
4. **Disabled с причиной, а не hidden** (образец — `PolicyActivity.why(bit)` [есть]).
5. **UI не делает сетевых запросов сам.** Читает локальный `status.json` и пишет намерения файлом/командой в нативную часть, как `PolicyActivity` и `InviteActivity` сегодня [есть].
6. **UI не источник правды о правах.** Кнопка включена, если нативная часть сообщила `eff` с нужным битом в нужном scope; финальная проверка всегда на исполнителе (0018 §5).
7. **Pending ≠ delivered ≠ applied.** Никогда не показывать «готово» по факту отправки.

## 2. Вход и защита от wrong-target

### 2.1 Что есть сейчас

- **[есть]** `TopologyView` → `OnPick.pick(dest, name)` → `MainActivity.select(dest)` пишет `state/select`. Короткий тап = выбрать выход.
- **[есть]** `adminBox` («Пригласить») показывается только при `pr.own()`. Право ADD от чужого админа кнопку не открывает; `grantedHeader` говорит это явно.
- **[есть]** Поля узла в `exits[]`: `d`, `id`, `n`, `adm`, `lk`, `vis`, `nh`, `pl`, `ra` и др. Тип узла: `pl` ∈ server/android/ios.

### 2.2 Предложение: три роли ноды на экране

| Роль | Что значит | Как отличать в UI |
|---|---|---|
| **Эта нода** (локальная, телефон) | я сам | подпись «Это вы», fingerprint из `whoami.json.hash` |
| **Выбранный выход** | через неё идёт трафик | текущая подсветка графа/списка (как сейчас) |
| **Администрируемая нода** | цель команды | отдельная шапка экрана «Управление», см. 3.1 |

Это три независимых понятия: админить можно ноду, которая не выбрана выходом, и наоборот. Выход нельзя менять «заодно» с админ-действием.

### 2.3 Точки входа [предложение]

1. **Граф:** долгое нажатие на узел (сейчас долгого нажатия нет; перетаскивание и двойной тап по пустому месту заняты) → небольшое меню: «Выбрать выходом» / «Управление…» / «Сведения». Короткий тап не меняется.
2. **Список нод** (`buildList`): справа у строки значок «⋯» → то же меню. Строка целиком — по-прежнему выбор выхода.
3. Пункт «Управление…» **виден всегда**, но включён только если по `status.json` у меня есть CONFIG/ADD/REMOVE в scope этой ноды (или я её прямой админ). Иначе disabled с причиной: «Нет права CONFIG на эту ноду», «Нода вне вашей сети» и т. п.
4. Для телефона как нода (`pl=android/ios`) «Управление» ограничено: он клиент/админ, не транзитный сервер [есть, AGENTS.md]. Показывать только участников/права, без host-функций.

### 2.4 Защита от wrong-target [предложение]

- Шапка экрана «Управление» всегда содержит: **имя ноды, страна/флаг, короткий fingerprint identity (первые 8 + последние 4 hex), тип**. IP/адрес **не показывать** вообще.
- Цвет/полоса шапки отличается от главного экрана; при выходе — обратно на главный без изменения выбранного выхода.
- Любое изменяющее действие переспрашивает **осмысленным текстом**, а не «Вы уверены?»: «Отозвать EXIT у *Телефон Анны* (fp a1b2…c3d4) на ноде *knothop-NL-1* (fp 9f8e…77aa)». Подтверждение — обычная кнопка в диалоге. Без биометрии и без системного запроса личности.
- Если между открытием экрана и подтверждением fingerprint цели сменился (нода пересоздана, имя то же) — действие блокируется, экран перечитывается.
- Одноимённые ноды различаются fingerprint, не только названием.
- При действии «на другой ноде» поверх экрана постоянная плашка «Цель: …», чтобы после сворачивания/возврата её не потерять.

## 3. Экраны

Новая `NodeAdminActivity` (`exported=false`, регистрируется как `InviteActivity`/`PolicyActivity` [есть]) с вкладками. Все вкладки читают один и тот же срез `status.json`; запись — через `Native.runVpn(...)`/атомарный файл намерений.

### 3.1 Статус ноды

```
┌ Управление ───────────────────────┐
│ 🇳🇱 knothop-NL-1          server   │
│ fp 9f8e3c21…77aa                  │
│ Роль для вас: делегат сети        │
│ Состояние: на связи (Link) · 12 с │
│ Данные от: сейчас / из кэша 14 мин│
├───────────────────────────────────┤
│ [Статус][Участники][Приглашения]  │
│ [Журнал]                          │
└───────────────────────────────────┘
```

- **[есть]** данные: `lk`, `vis`, `nh`, `ra`, `q`, `c`, `h`, `r` из `exits[]`.
- **[предложение]** «Данные от: …» — возраст среза. Устаревшее помечается, не скрывается.
- **[нет backend]** удалённые счётчики/нагрузка чужой ноды по запросу; сегодня видно только то, что уже в `status.json`.
- Роль: «Администратор этой ноды» / «Администратор сети» / «Делегат» / «Только просмотр». Определяется из цепочки прав (раздел 4), не из тега.

### 3.2 Участники и права

```
┌ Участники ────────────────────────┐
│ Анна (телефон)  fp a1b2…c3d4      │
│   USE ✓  EXIT ✗  TRANSIT —        │
│   выдал: вы · до 2026-11-20       │
│   [Изменить] [Отозвать]           │
│ Борис (ноутбук) fp 5c6d…e7f8      │
│   USE ✓  EXIT ✓                   │
│   ⏳ отзыв EXIT в очереди (offline)│
└───────────────────────────────────┘
```

- **[есть]** `status.json.users[]` и холдеры в цепочках `trust.rs`; CLI `revoke` [по Android-коду; сверить].
- **[нет backend]** полный список холдеров *чужой* ноды по запросу; отзыв из UI не подтверждён как законченная функция (AGENTS.md); точечный REMOVE и видимость холдеров админом — 0019 §8.5.
- **Два разных вида действий, UI их не смешивает:**
  1. **Локальное управление своим корнем** — запись подписанного отзыва/записи в локальное trust-хранилище этого телефона (то, что делает локальный CLI). Это **не** remote admin и **не** означает, что target-нода получила или применила отзыв. Результат в UI: «Записано локально», с подписью «Нода ещё не уведомлена».
  2. **Адресное выполнение на target** — команда target-ноде по штатному RNS/LXMF с прикладным application commit ACK. Только это даёт статус «Применено на ноде».
- Кнопки адресных действий (выдать/отозвать на target-ноде) показываются, но **disabled с причиной**, пока backend не объявил поддержку адресных команд на target («Нода/приложение не поддерживают удалённые команды»). Статус «применено» **никогда** не ставится по exit code 0 локального CLI.
- «Изменить» открывает чекбоксы USE / TRANSIT / EXIT (и **будущий** HOST_ACCESS). Каждый чекбокс:
  - включён, если мои эффективные права и delegation limit позволяют выдать этот бит в этом scope;
  - иначе disabled с причиной: «Нельзя выдать больше, чем есть у вас», «Лимит делегирования: только USE», «TRANSIT на телефон не выдаётся».
- Для ВЫДАЧИ показывать итог-превью «Что получит холдер»: список битов человеческим языком и срок.
- HOST_ACCESS (**[нет backend]**, не реализован): строка «Доступ к службам самой ноды», подпись «Все порты и протоколы ноды. Не локальная сеть и не Docker». Чекбокс disabled с причиной «Не поддерживается этой версией ноды», пока не придёт capability от ноды. Выдача и отзыв — только админом ноды или сети в scope реальных цепочек. Свой root прав на чужих узлах не создаёт — в UI никаких «я root, значит можно».
- Отзыв HOST_ACCESS: текст «Существующие подключения к службам ноды будут закрыты» (так задумано: проверка до TUN, revoke закрывает потоки) — показывать только если нода объявила поддержку.

### 3.3 Приглашения и журнал

```
┌ Журнал ───────────────────────────┐
│ 10:42 Выдано USE+EXIT  Анне       │
│       ✓ применено · v7            │
│ 10:40 Приглашение на 3 ноды       │
│       2 из 3 готовы (ACK)         │
│ 09:15 Отзыв EXIT  Борису          │
│       ⏳ ждёт доставки · истекает │
│       через 9 мин                 │
└───────────────────────────────────┘
```

- **[нет backend]** журнал действий как хранилище и источник истины. Вкладка «Журнал» — это **проекция (read-only view)** состояния, которое ведёт штатный durable executor/LXMF-очередь нативной части: pending, результаты, отзывы. UI **не строит собственный outbox и не вводит свой протокол очереди** (`AdminLog` как источник статуса не создаётся). Допустим только локальный кэш отображения (производный, пересобираемый из состояния нативной части), в который можно записывать лишь то, что нативная часть сообщила: command id (короткий префикс), цель по fingerprint, действие, статус, времена. Не содержит pin, строк `kh-`, ключей.
- Если нативная часть durable-состояния команд не отдаёт, вкладка показывает только локальные события («записано локально», «приглашение выдано») с пометкой «не подтверждено нодой».
- Журнал **не** претендует на аудит всей сети; подпись под списком: «Показаны действия, сделанные с этого телефона».
- Выданные приглашения: статус «ждёт ACK / готово / показано / принято / истекло», срок 48 ч (0019). Строку приглашения повторно не хранить и не показывать — после ухода с экрана она стирается (как `InviteActivity` сегодня [есть]).

### 3.4 Роли 0015

- **[есть]** `PolicyActivity` («Мои права») — политика *локальной* identity: сужение выдачи, скрытие нод без прав.
- **[предложение]** вкладка «Роли» в «Управлении» **не создаётся**, пока не появится реальная поддержка конфигурации ролей чужой ноды. Ссылка «Мои права» остаётся на главном экране. Если логика 0015 позже получит удалённую конфигурацию — это отдельная вкладка с теми же правилами disabled-с-причиной.

## 4. Прямой админ vs сетевой админ/делегат; effective permissions

### 4.1 Как объяснять права

Раздел «Почему я могу/не могу» (разворачиваемый блок под шапкой ноды):

```
Ваши права на эту ноду:
 ✓ CONFIG  — по цепочке: Root «Сеть Марата» → вы
 ✓ ADD     — то же, лимит: USE, EXIT
 ✗ REMOVE  — не выдано
 ✗ HOST_ACCESS — нода не поддерживает
Ограничение делегирования: глубина 1
```

- **[есть]** `status.json.policy[]` уже содержит `root`, `tag`, `grant`, `eff`, `offer`; `trust.json` — `anchors`. Источник для текста.
- **[предложение]** UI показывает **корень (root)** и **кто выдал**, а не только «есть/нет». Человекочитаемое имя root берётся из локальных данных; fingerprint — всегда рядом.
- Различать три источника:
  1. **Прямой админ своей ноды** — моя identity является root этой сети/ноды. Всё доступно в пределах цепочки.
  2. **Сетевой админ** — права по цепочке от root, scope = сеть.
  3. **Делегат** — права с ограничением (лимит битов, scope по нодам, глубина).
- **Authority определяется не категорией «моя/чужая сеть», а:** принятым локальным anchor, подписанной делегацией/цепочкой и scoped rights **на конкретную target-ноду**. UI не вводит собственного деления «своя/чужая». Возможно, что у человека валидная делегация или админство сразу в нескольких сетях; возможно, что собственная identity прав на target не даёт (self identity ≠ право), а принятая делегация от другого root — даёт.
- Поэтому экран считает **effective authority для пары (я, target)** по данным нативной части и показывает причину в обоих исходах:
  - есть право: «CONFIG на NL-1: делегация от root *Сеть А* (fp …), принят локальный anchor, scope: NL-1, DE-1, глубина 1»;
  - нет права: «Нет подписанной цепочки до принятого вами anchor, дающей CONFIG на NL-1» или «Ваш собственный root не имеет прав на этой ноде; делегаций от её root вы не принимали».
- Если нативная часть не может вычислить authority для target (нет данных/цепочки), кнопки disabled с причиной «Права на эту ноду не определены», а не «чужая сеть».
- Если у target несколько применимых цепочек (разные root), UI показывает их списком и предлагает выбрать, от какой выполняется действие; по умолчанию — самая узкая, достаточная для действия.
- Расхождение: UI считает право, нода — нет (отозвано, устарело) → результат команды `rejected: stale rights`; UI после этого обновляет срез и объясняет причину.

### 4.2 Приватность и экспорт нод

- Ноды могут иметь локальную настройку приватности/экспорта (что показывать в топологии, 0018). UI **обязан уважать её**: если нода скрывает холдеров/адреса/метки, то даже при общей топологии вкладки «Участники» и «Статус» показывают только разрешённое.
- Пустой блок подписывается причиной: «Нода не публикует список участников», а не пустым экраном.
- Никаких IP, внутренних адресов, имён интерфейсов и меток VPN в публичном UI и в анонсе (AGENTS.md п.9).

## 5. LXMF offline UX

**[нет backend]**: LXMF в knothopd не подключён, команды к чужой ноде не реализованы. Раздел описывает UX, который нужен, когда backend появится (0018 §4.4, §5, §6). До этого MVP работает только с нодами на связи через уже существующее соединение.

### 5.1 Четыре состояния команды

| Статус | Иконка | Смысл | Что разрешено |
|---|---|---|---|
| **Подготовлено** | ✎ | сформировано локально, не отправлено | отменить |
| **В очереди / отправлено** | ⏳ | ушло в LXMF/Link, доставки нет | отменить (best-effort), ждать |
| **Доставлено** | 📨 | нода получила сообщение | ждать результата |
| **Применено** | ✓ | нода ответила прикладным результатом с operation ID и применённой версией | — |
| **Отклонено / истекло / конфликт** | ✗ | см. 5.3 | повторить с новым состоянием |

- «Применено» — **только по прикладному ответу** ноды, не по доставке (0018 §4.4).
- Pending-команда на офлайн-ноде отображается постоянно в строке участника и в журнале.

### 5.2 Command id и идемпотентность

- Каждое действие получает `command_id` (случайный, не выводится пользователю целиком; в журнале — короткий префикс).
- «Повторить» отправляет **ту же** команду с тем же `command_id`; нода обязана идемпотентно вернуть тот же результат. UI не создаёт новых id при повторе — иначе возможна двойная выдача.
- «Отменить» pending-команды — это **новая** отменяющая команда (или локальное снятие до отправки), а не удаление из журнала.

### 5.3 Expiry, конфликт, версия, устаревшие права

- По 0018 §5: команда ≤ 4 КиБ; опасная (отзыв, выдача битов) TTL 10 мин, обычная 24 ч; не больше 32 pending на issuer. UI показывает **оставшееся время**: «истекает через 9 мин».
- Истёкшая опасная команда не отправляется автоматически позже. Кнопка «Повторить сейчас» формирует новую команду после обновления среза.
- Конфликт версий: нода ответила «версия состояния изменилась» → UI показывает «Состояние ноды изменилось. Обновите и проверьте». Выбор пользователя не применяется молча.
- Устаревшие права: если мои права к моменту исполнения отозваны, нода отклонит; UI объясняет «Ваше право CONFIG больше не действует».

### 5.4 Revoke на офлайн-ноде

Критично для честности:

```
⚠ Нода knothop-NL-1 не на связи.
Отзыв EXIT у Бориса ещё НЕ вступил в силу на этой ноде.
Пока она не получит команду, Борис может выходить через неё.
```

- Строка участника показывает «⏳ отзыв ждёт ноду», а не «отозвано».
- Если отзыв выпущен как подписанная запись (trust-цепочка), он действует везде, где запись уже получена; про ноды, где её нет, UI честно пишет «покрыто N из M нод» (сопоставимо с partial coverage, 6.3).

### 5.5 Частота и push

- **Никакого polling раз в 1 с** по сети и никаких фоновых полных графов. Сегодняшний таймер 1 с читает **локальный файл** — это допустимо и остаётся [есть].
- Данные админ-экранов — **из кэша** `status.json` плюс **события** (event push от текущего выхода по Channel subscription, 0018 §6). Экран при открытии показывает кэш с возрастом, сеть запрашивает один раз и далее ждёт событий.
- Кнопка «Обновить» — ручная, с лимитом частоты (не чаще раза в 10–15 с, по решению logic-агента).
- Android не получает push для спящего LXMF → ответы на офлайн-команды видны при следующем запуске/подключении; уведомление «Результат команды готов» — только если уже есть работающий сервис и это не расходует бюджет idle (≤2 МиБ/сут, 0018).

## 6. Invite flow по 0019

### 6.1 Сейчас [есть]

`InviteActivity`: 2 шага → выбор нод (`adm=true`, 32-hex `id`) и пресет прав → `Native.runVpn("invite --state … --rights … --nodes …")` → строка/QR, `FLAG_SECURE`, стирание при уходе. Текст «30 дней», эмодзи, `Confirm.ask` (по умолчанию пропускается, `ADMIN_CONFIRM=false`). Приглашение v3 (`kh-`, `knothop://i/`), TTL 30 дней в `Profile.INVITE_TTL_S`.

### 6.2 Цель 0019 [нет backend]

Приглашение v4: до 8 нод, права только USE/TRANSIT/EXIT (`cap ⊆ 0x07`), TTL 48 ч, сначала ACK от нод, потом показ строки, `complete` по `ENROLL_NODES`, commissioner после закрытия PIN возвращает per-node scoped права.

### 6.3 UI flow [предложение]

```
Шаг 1  Выберите ноды            (≤ 8)  ← из тех, где вы админ
  [x] 🇳🇱 NL-1   fp 9f8e…77aa   ✓ готова
  [x] 🇩🇪 DE-1   fp 21aa…03bc   ⏳ офлайн (нужна для ACK)
  [ ] 🇫🇮 FI-1   fp ....        — нет прав ADD

Шаг 2  Права для нового участника (единые для выбранных нод)
  (•) Пользователь: USE + EXIT
  ( ) Расширенный:   + TRANSIT
  Срок билета: 48 ч · одноразовый
  Нельзя больше, чем даёт ваша цепочка и лимит делегирования.

Шаг 3  Согласование с нодами
  NL-1  ✓ ACK     DE-1  ⏳ ждём ответа
  Не ответили: DE-1
  [Подождать ещё]
  [Продолжить без DE-1]   ← явный выбор, не молчаливое сужение
  (если ACK нет ни от одной ноды — «Продолжить» недоступно: выпуска нет)

Шаг 3б Подтверждение частичного охвата (если выбрано «без DE-1»)
  «Приглашение будет действовать только на: NL-1.
   DE-1 в него не войдёт. Если DE-1 позже ответит, доступ
   на ней по этому приглашению не появится.»
  [Назад] [Показать приглашение]

Шаг 4  Строка / QR (FLAG_SECURE)
  Действует до 21:40 · одноразовое
  Покрытие: 1 из 2 выбранных нод (NL-1)
```

Правила:

- **Единые права** на все выбранные ноды — одна форма, не по ноде (простота; per-node scoped права возвращает commissioner на backend, не UI).
- **ACK-готовность** по каждой ноде — отдельный индикатор. По 0019 §«Выпуск» (шаги 6–7, «Недоступность нод при выпуске»): ноды без ACK в приглашение не входят, приглашение показывается при **≥1 ACK**, при нуле ACK выпуска нет. Это уже решение ADR, UI **не вводит** новое правило «показывать только когда ответили все».
- **Явный выбор для не ответивших:** пока есть выбранные ноды без ACK, UI предлагает два действия — «Подождать» и «Продолжить без них» — и не сужает список и права молча. «Продолжить без них» ведёт на экран подтверждения частичного охвата (шаг 3б) со списком исключённых нод по именам и fingerprint.
- **Partial coverage** честно: «Приглашение работает на 1 из 2 выбранных нод» — везде, где охват меньше выбранного: на шаге подтверждения, на экране строки/QR и в записи журнала приглашений.
- Для исключённых нод, которые могли получить грант без ACK, UI пишет то, что говорит 0019: если нода доступна, ей шлётся `GrantRevoke`; если нет, её `H_store` остаётся до `expires` и безвреден до истечения. UI не обещает «отозвано», пока нет подтверждения.
- Если нода ответила ACK **после** того, как строка уже показана, она в эту строку не входит (хеши в строке фиксированы).
- **Эмодзи и `Native.toEmoji` убираются**; остаётся `kh-` строка/QR/deep link. Текст «30 дней» заменяется на «48 часов».
- **Системное подтверждение личности не возвращается.** Перед показом строки — обычный экран-итог «Кого и куда вы приглашаете: права, ноды, срок» и кнопка «Показать». Этого достаточно по 0019.
- **Предупреждение при показе:** «Это одноразовый билет. Любой, кто увидит строку до погашения, сможет по ней войти. Не публикуйте её».
- Отзыв до погашения (`GrantRevoke`, 0019): кнопка «Отозвать приглашение» в журнале приглашений, пока статус не «принято».
- Телефон как нода гранта работает **только при запущенном приложении** (очистка данных теряет pin): при выборе телефона в шаге 1 подпись «Только пока приложение запущено».
- Приглашения на PN-ноды только серверные — в шаге 1 телефоны как PN не предлагаются.

## 8. Accessibility, языки, тесты, согласованность, безопасность

### 8.1 Accessibility

- Статус не только цветом: иконка + текст («⏳ ждёт», «✓ применено»).
- Граф для TalkBack недоступен по природе; список нод — основной доступный путь; «⋯» имеет `contentDescription` с именем ноды и fingerprint.
- Минимальная цель нажатия 48 dp; диалоги подтверждения читаются целиком.
- Fingerprint можно скопировать/прочитать по группам по 4 символа; QR/строка приглашения — `FLAG_SECURE`, без автокопирования в буфер.

### 8.2 Языки

- Русский и английский обязательны; строки статусов команд и причин — в ресурсах, не склеивать из кусков.
- Идентификаторы прав (USE/TRANSIT/EXIT/…) остаются латиницей рядом с переводом («Выход в интернет (EXIT)»), чтобы совпадать с документацией.
- Названия ноды берутся из `knothop-XX-имя` через существующие `shortName/countryName/flagOf`.

### 8.3 Тесты

- UI-тесты на офлайн: нода не на связи → команда в очереди → применено/истекло; повтор с тем же `command_id` не создаёт дубль.
- Тест wrong-target: смена fingerprint цели между открытием и подтверждением блокирует действие.
- Тест disabled-с-причиной: для каждого бита и каждого источника отказа есть текст.
- Тест `FLAG_SECURE` и стирания строки приглашения при уходе с экрана (регресс).
- Лабораторные интенты — только в `KNOTHOP_LAB=1`, в обычной APK их нет.
- Не запускать на публичной RNS: тесты только в изолированной лаборатории (`lab13.py`).

### 8.4 Согласованность

- После каждого изменяющего действия экран **не** считает результат успешным, пока не придёт новый срез с применённой версией.
- Если срез старше порога (например 10 мин), в шапке «Данные устарели», изменяющие кнопки остаются, но с пометкой, что действие уйдёт в очередь.
- Двойной отзыв/выдача защищён `command_id`; два админа, меняющие одно и то же, получают конфликт версии (5.3), а не «последний выиграл молча».

### 8.5 Безопасность

- Не выводить и не логировать: seeds, private key, pin, `kh-`/`knothop://i/` строки, IP/адреса нод. В журнале хранить только fingerprint, действие, статус.
- Строка приглашения: только в памяти Activity, `FLAG_SECURE`, стирается при `onPause/onStop`.
- Все вызовы нативной части — через уже существующий `Native.runVpn(args, stateDir)`; аргументы не содержат секретов (сегодня `invite` — исключение владельца; предпочтительно файл 0600, как рекомендует AGENTS.md).
- UI не повышает права по заявленной роли/тегу: роль на экране — вывод из цепочки, не из имени ноды.
- Всё полученное от ноды (имя, текст ошибки, список участников) недоверенный ввод: ограничение длины, никакого HTML/ссылок, экранирование.
- Открытый Link ≠ доверенный пир: «на связи» в статусе не означает права; права показываются отдельно.

## 9. Этапы MVP

| Этап | Содержание | Зависимость |
|---|---|---|
| **M0** (UI без backend) | Долгое нажатие/«⋯» → «Управление»; шапка с fingerprint и ролями (3 роли ноды); блок «Почему я могу/не могу» из `status.json.policy[]`; вынос `why(bit)`; удалить эмодзи; текст 48 ч там, где уже безопасно | нет |
| **M1** (только просмотр + локальное управление своим корнем) | Вкладка «Участники»: чтение списка из `status.json`. Действия изменения — либо отсутствуют, либо это **локальная запись в своём корне** с честным статусом «записано локально, нода не уведомлена». Адресные пункты «выдать/отозвать на target» показаны **disabled с причиной**, пока backend не поддерживает target commands. Никакого «применено» по exit 0 локального CLI. Журнал — проекция того, что отдаёт нативная часть | локальная запись отзыва из UI надо подтвердить законченной функцией; к remote admin отношения не имеет |
| **M2** (Invite v4) | Шаги ACK/покрытие, единые права USE/TRANSIT/EXIT, 48 ч, `ENROLL_*`, ввод `complete`; убрать `Confirm` | Invite v4 и `ENROLL_*` (0019) |
| **M3** (адресное управление; **remote MVP**) | Включение адресных кнопок для target-ноды; состояния pending/delivered/applied; `command_id`; expiry/conflict | **Native RNS/LXMF target commands** и **application commit ACK** от ноды, durable executor с pending/results/revocations, event push по Channel, scope и capabilities в `status.json`. Без этого remote MVP не включается; UI не заменяет их собственным протоколом или outbox |
| **M4** (HOST_ACCESS) | Строка «Доступ к службам ноды» в выдаче/отзыве | реализация фичи HOST_ACCESS и capability от ноды |
| **M5** (журнал сети) | Серверный/общий журнал действий, а не только локальный | backend журнала |

**Откат.** Короткий тап/выбор выхода не затрагивается ни одним этапом. Откат разделяется на два уровня:

- **Откат UI до появления активных команд (M0–M1):** можно скрыть/удалить точки входа и новую Activity.
- **После появления активных команд (M3 и далее):** откат UI — это только скрытие экрана. Он **не** удаляет и **не** отменяет durable pending-команды, результаты и отзывы (revocations) в нативной части, и не отменяет уже применённую на ноде команду. Pending-команды продолжают исполняться или истекать по TTL; применённые не откатываются. При скрытом UI остаётся минимальный индикатор «есть неподтверждённые команды» (без возможности отправлять новые) либо явный отказ откатывать, пока pending не разобраны. Отмена конкретной команды — отдельная явная отменяющая команда (5.2), а не побочный эффект отката UI.
- **Права приложения не расширяются** под удалённые shell/reboot/firewall/systemd: новых Android-разрешений и обработчиков для них нет ни на одном этапе. Новая Activity — `exported=false`, без новых permissions сверх существующих.

## 11. Открытые вопросы владельцу

2. Достаточна ли для MVP журнал-проекция состояния нативной части (только действия с этого телефона), или нужен общий серверный журнал?

4. Допустим ли rate-limit ручного «Обновить» 10–15 с, или нужно строже?
5. Какой порог «данные устарели» (по умолчанию 10 мин)?
