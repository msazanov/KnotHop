## 0. Короткий итог

1. **Грант и отзыв прав — подписанная `Record`** (семантика Record переиспользуется как есть); команда нужна только там, где ключ подписи у самой ноды (`Policy`, локальный конфиг) и для чтения статуса. Адресная доставка и записей, и команд — **RNS-native/LXMF**, а не «T_REC навсегда»: `T_REC` остаётся механизмом gossip состояния между допущенными соседями, но не адресным каналом remote admin.
2. **Remote-admin MVP зависит от LXMF.** Request/Response онлайн допустим как второй носитель **той же** операции (одна семантика, один формат тела), но MVP считается готовым только с LXMF-путём. Свои crypto/транспорт/outbox не пишем; наше остаётся — проверка прав при применении, журнал идемпотентности, прикладной ACK durable commit.
3. **`HOST_ACCESS = 64`**, действует на конкретной ноде-адресате и только на **точные** адреса этой ноды (не на подсети). Выдать его может админ **своей ноды** (own-root, по природе node-specific) и/или **админ сети** — по цепочке до **принятого этой нодой якоря**. Сетевая выдача на конкретную ноду в MVP возможна **только** при валидном scoped-доказательстве (scoped-права ADR 0019); пока его нет, она **отключена** (явная зависимость), а не подменяется root-wide записью (§2.2). Нода сама определяет, каким network authorities она доверяет; multi-root допускается. OR прав несвязанных якорей, «весь CONFIG сетевому админу» и автоматический `CONFIG` вместе с `HOST_ACCESS` исключены.
4. **Исполнение — в приложении, до TUN**: явный default-deny для всего, что не публичный интернет и не точный разрешённый адрес самой ноды (private/loopback/special/неклассифицированное), проверка версии/длины/фрагментов и обоих направлений, ответы per identity, IPv6 — отказ. nft — **только defense in depth**, не backend прав и не условие работы функции; динамические nft-sets и обновление nft на каждый grant не нужны. Но есть честный технический блокер доставки: действующий статический `client->node` drop в INPUT (§4.4).
5. Что осталось по-настоящему неопределённым — §7.

## 2. Модель прав

### 2.1 Биты и маски **[проверено в коде]**

| Бит | Знач. | Где исполняется сегодня |
|---|---|---|
| `USE` | 1 | `common_with(EXIT, USE)` в `evaluate`, `admit_client13` |
| `TRANSIT` | 2 | `common_with(TRANSIT, TRANSIT)`, `visible` |
| `EXIT` | 4 | то же, `holders_with(EXIT)` |
| `ADD` | 8 | `issue`, `validate_invite_rights`, экспорт |
| `REMOVE` | 16 | `issue` при `rights==0` |
| `CONFIG` | 32 | только видимость экспорта; **операций нет** |
| `HOST_ACCESS` | **64 (новый)** | ACL приложения (§4) |
| ≥128 | — | **неизвестны: reject на parse** (как сейчас) |

Текущие маски и места: `ALL=63`; `PRESET_ADMIN=ALL`; `PRESET_RELAY=USE|TRANSIT|EXIT|ADD`; корень получает в `eff` `ALL` по определению. Валидаторы `rights & !ALL`: `Record::parse`, `Policy::parse/sign`, `parse_rights`, `set_my_policy`, загрузка `mypol`, `vpn.rs:5307`; тест `vpn.rs:~1247`; Java: `InviteActivity.R_NAME` (6 элементов), `Profile.java:117` (`~63`).

**Предложение (не принятое решение владельца) без скрытого изменения модели:**

- Ввести `KNOWN = 127` — **только** маска валидации формата (parse/sign/load/invite). Неизвестные биты (`& !KNOWN != 0`) **отвергают запись/политику/приглашение целиком**; «обрезать» их маской (`& KNOWN`) и принимать остальное запрещено — иначе нода молча применит часть прав, которых издатель не имел в виду.
- `HOST_ACCESS` никогда не приносит `CONFIG` (и любой другой бит) автоматически: ни в пресетах, ни в UI, ни в приглашении. Запись заменяет маску целиком (`seq`), поэтому выдача `HOST_ACCESS` держателю с `USE` формирует ровно `USE|HOST_ACCESS` (клиент собирает `old | 64`, а не берёт пресет).
- `ALL` **не менять** (=63): все существующие записи и пресеты (`PRESET_ADMIN`, `PRESET_RELAY`, 0019 `cap ⊆ 0x07`) сохраняют значение. Побочное явное уточнение, которое придётся принять: «админ-пресет» **перестаёт быть синонимом полной власти** — полная власть корня определяется отдельно.
- **Полная власть корня** (`eff(root, root)`): остаётся «все **известные** биты» — то есть `KNOWN`, а не `63`. Иначе владелец корня не смог бы делегировать `HOST_ACCESS`. Это единственное семантическое расширение root authority; оно не касается ни одной уже выданной записи: старые записи ≤ 63 интерпретируются как прежде, `PRESET_ADMIN` не получает бит 64 молча.
- Mixed version: старая нода отбрасывает запись с битом 64 **целиком** (включая `USE`/`EXIT` в той же записи) — **[проверено: `Record::parse`]**. Поэтому запись с `HOST_ACCESS` допустимо выпускать держателю только после того, как все ноды, которые примут эту запись (получатели доставки и соседи по gossip), имеют capability (§2.5, coverage check); иначе держатель потеряет и `USE`/`EXIT` на старых нодах. Это правило раскатки, а не молчаливый downgrade.

### 2.2 Authority для `HOST_ACCESS`: принятые якоря + scope

Нода N определяет **множество host-authorities** `HA(N)`:

- свой собственный корень (`me_hash`) — всегда;
- **любой принятый N якорь** R, который N явно пометила как `host_trust` (локальная настройка уровня N: список якорей, максимум в пределах `MAX_ANCHORS=8`). Список может содержать несколько корней — multi-root реален.
- **Не** входят: чужой собственный root, не принятый как якорь (foreign self-identity root — не полномочие); принятые, но не помеченные `host_trust`, якоря.

Для каждого R ∈ HA(N) решение считается **внутри одной цепочки**:

```
host_in(R, H, N, now) =  rights_in(R,H) & HOST_ACCESS != 0         # цепочка до якоря R, подписи, отзыв, глубина, delegation caps
                      ∧ scope_ok(record, N)                          # см. ниже
                      ∧ N.offer(R) & HOST_ACCESS != 0 (не просрочена) # offer ограничен потолком владельца, §2.3
```

`scope_ok(record, N)` — единственные два допустимых случая в MVP:

1. **own-root N:** `record.root == hash(N)`. Корень — сама нода, запись node-specific по природе.
2. **network, на конкретной ноде:** есть **валидное scoped-доказательство** для N (scoped-запись `EnrollRec` по 0019 с `scope = hash(N)` либо иное подписанное свидетельство той же силы), проверенное при исполнении: подпись, цепочка до R, срок, отзыв, `scope == hash(N)`.

Иначе `scope_ok = false`, **fail-closed**. В частности, обычная `Record` v1 сети X с битом 64 (она root-wide: поля scope нет) **не даёт** `HOST_ACCESS` ни на одной ноде: бит в ней хранится (и не мешает `USE`/`EXIT`), но для `host_in` игнорируется. Node-specific сетевую выдачу **нельзя** молча заменить root-wide записью. Пока scoped-механизма в коде нет (0019 не реализован), **network-grant `HOST_ACCESS` отключён** как явная зависимость MVP; работает только own-root.

Root-wide выдача («все ноды корня R, доверяющие R») — **отдельная, явно названная операция** вне MVP, не fallback: отдельный тип/флаг, отдельное подтверждение в UI с перечнем затронутых нод, и нода учитывает её лишь если владелец явно разрешил это для R в `host_trust` (`rootwide: true`). Она никогда не включается автоматически как запасной путь, если scoped-механизм недоступен.

Итог для держателя H на ноде N: `host_ok(N,H) = ¬local_deny(H) ∧ ∃ R ∈ HA(N): host_in(R,H,N,now)`. Это **не** OR прав по несвязанным якорям: каждое решение собрано внутри цепочки одного корня и хранит `root` как источник; бит никогда не вычисляется через `Trust::rights()`/`effective()` (они делают OR по всем якорям — **[проверено: `trust.rs:627,774`]**; для `HOST_ACCESS` запрещены). Мульти-root — набор независимых вкладов, помеченных корнем.

**Приоритеты и конфликты (предложение, не owner decision):**

1. `local_deny(H)` — явный локальный запрет владельца ноды, перекрывает всё. Предлагается как отдельный механизм приоритета; owner decision в §7.
2. Запись в **own-root** (включая `rights=0` — явный отказ) — решение владельца ноды; если она есть, вклады network-якорей не рассматриваются (владелец может и выдать, и забрать).
3. Иначе — независимые вклады network-якорей из `HA(N)` (в MVP их нет: network-grant включается только после S1b, §5.1); отзыв в сети X убирает только вклад X; доступ через Y остаётся. UI обязан показывать это: «отозвано в X, доступ сохраняется через Y».

Тихих union-ов нет: каждый вклад явный, помечен корнем, доверие к корню — локальное решение ноды.

### 2.3 Delegation caps и CONFIG по классам

`ADD`+`HOST_ACCESS ⊆ mine` для выдачи (существующее правило `issue`: `rights ⊆ mine`, глубина ≤ 8, квоты); `REMOVE` для отзыва; делегат без `ADD` дальше не передаёт. `HOST_ACCESS` не выводит `CONFIG` (самовыдача невозможна) и не выдаётся вместе с ним автоматически.

`CONFIG` **не** отдаётся сетевому админу целиком. Это права по классам операций, определяемые по источнику авторитета:

| Класс | Кто может | Пример |
|---|---|---|
| node-local | CONFIG в **own-root** | список `host_trust`, алиасы адресов, local deny, потолок offer в корне R |
| network-policy | CONFIG в R, **в пределах потолка** (`ceiling(R)`), установленного own-root | `policy.set(R, offer)`: включить/выключить USE/TRANSIT/EXIT и (если потолок позволяет) `HOST_ACCESS` в R |
| read | любое из ADD/REMOVE/CONFIG в общем корне | `status.get` (scoped) |

Потолок означает: владелец ноды решает, **сколько** власти нода передаёт сети X (в том числе `HOST_ACCESS`); сетевой CONFIG действует внутри. Так «админ сети может выдать право доступа к службам этой ноды» достигается без передачи ему управления нодой, а решение о доверии остаётся за нодой.

### 2.4 Матрица операций

| Операция | Требуемое у актора | Корень | Где проверяется |
|---|---|---|---|
| Выдать USE/TRANSIT/EXIT | `ADD`, `rights ⊆ mine` | любой принятый | `issue`/`offer` |
| Выдать `HOST_ACCESS` на N — own-root | `ADD` + `HOST_ACCESS ∈ mine` в корне N | own-root N | `issue`; на N — `host_in`; node-specific по природе |
| Выдать `HOST_ACCESS` на N — через сеть R | `ADD` + `HOST_ACCESS ∈ mine` в R **и** валидное scoped-доказательство для N | R ∈ HA(N) | на N — `host_in` с `scope_ok`; **отключено, пока scoped-механизма нет**; coverage check при нескольких нодах (§2.5) |
| Root-wide выдача `HOST_ACCESS` (отдельная операция) | `ADD` + `HOST_ACCESS ∈ mine` в R | R, явно `rootwide` в `host_trust` N | вне MVP; не fallback двух строк выше |
| Полный отзыв | `REMOVE` | тот же R | `issue` |
| Частичное понижение | сейчас `ADD`; вопрос §7 | тот же R | `issue` |
| `policy.set(R, …)` | CONFIG в R (в пределах `ceiling(R)`) | R | при применении на N |
| `config.set` (node-local) | CONFIG в own-root N | own-root | при применении |
| `status.get` | ADD/REMOVE/CONFIG в общем корне | общий | при применении; own-root — полный, network — scoped |

Роли `USE/TRANSIT/EXIT` для admin-запросов не нужны: отдельный endpoint, авторизация по identify + цепочке на момент запроса; Link не обязан быть допущен как VPN-клиент (0018 §4.5: whitelist enroll-only CBC не расширять).

### 2.5 `effective rights per (actor, target)` — контракт для UI

Нативная часть отдаёт на каждую пару (я, target) структуру (в `status.json`), чтобы UI [раздел 4.1](mobile-node-administration-ui-2026-10-23.md) не вычислял права сам:

```
eff_host[target] = {
  capable: bool,                       # нода объявила capability host_access (после authenticated status; в анонс не кладётся)
  authorities: [ {root, trusted: bool, grant: bool, scope: "own"|"node-scoped"|"root-wide(ignored)", depth, ceiling: bool, offer: bool} ],
  can_issue: bool, can_revoke: bool,   # из ADD/REMOVE + HOST_ACCESS ⊆ mine по каждому корню; can_issue для network-корня = false без scoped-доказательства
  inventory: "ready"|"stale"|"unsynced",  # §4.2; не ready => host_ok не действует
  addresses: u16,                      # число точных разрешённых host-адресов (host_allow); сами адреса не отдаются в status
  reason: enum { NO_CHAIN, ROOT_NOT_TRUSTED_BY_NODE, NODE_NOT_CAPABLE, NO_OFFER, LOCAL_DENY, EXPIRED_POLICY,
                 NETWORK_SCOPED_BACKEND_MISSING, NO_ALLOWED_ADDRESSES, INVENTORY_NOT_READY, UNKNOWN }
}
```

При нескольких применимых корнях UI показывает список и предлагает выбор корня выдачи (по умолчанию — самый узкий достаточный), как в UI-proposal §4.1. **На конкретном target UI выдаёт только то, что реально ограничено этой нодой** (own-root либо scoped-доказательство); он никогда не создаёт невидимое право «на все ноды корня». Если доступна лишь root-wide — кнопка выдачи на target отключена с причиной `NETWORK_SCOPED_BACKEND_MISSING`; root-wide — отдельное явно названное действие (§2.2), не показывается как «выдать на эту ноду». Нода всё равно проверяет заново; `rejected: stale rights` — штатный исход.

**Coverage при выдаче на несколько нод** (в т.ч. приглашение): единая маска `HOST_ACCESS`-грант допустим только если issuer имеет `host_in`-авторитет на **каждой** выбранной ноде (корень ∈ HA(n), нода capable, потолок позволяет). Иначе — явный отказ или явное исключение ноды в UI с показом покрытия («работает на k из n»), без молчаливого сужения.

### 2.6 Приглашения

ADR 0019 фиксирует `cap ⊆ 0x07` (USE/TRANSIT/EXIT), а ADD/REMOVE/CONFIG остаются открытым вопросом (0019 §16). Для `HOST_ACCESS` **владелец запрета не принимал**, поэтому этот документ запрет **не фиксирует**. Варианты `cap` в Invite v4 (решение владельца):

1. `cap ⊆ 0x07` (как в ADR сейчас; `HOST_ACCESS` — отдельным грантом после зачисления);
2. `cap ⊆ 0x47` (с `HOST_ACCESS`), **при условии** coverage check §2.5 на каждой выбранной ноде: каждая нода при `ENROLL_CLOSED` сама проверяет `host_in` для issuer'а и выдаёт свою scoped-запись (`scope = она`) с `HOST_ACCESS` или честно отвечает отказом по этому биту. Никакого blacklist бита по умолчанию.
3. Отдельная операция выдачи после зачисления.

Технически вариант 2 естественно ложится в 0019: нода, терминирующая доступ, сама решает, давать ли бит по своей `HA(N)`, и выдаёт именно scoped-запись для себя (не root-wide); но это зависит от реализации scoped `EnrollRec` (в коде **ещё нет**). До неё варианты 1 и 3 действуют только как own-root выдача; бит 64 в приглашении без scoped-механизма не превращается в root-wide право.

## 3. Жизненный цикл команды телефон → нода

### 3.1 Носитель и семантика

Одна операция — один формат тела `AdminCmd`; два носителя: **LXMF** (адресная доставка, офлайн; обязательная часть MVP) и **Request/Response** онлайн (допустимый быстрый путь для той же операции, `status.get` — только онлайн). Подпись LXMF-источника и доставка (PN, delivery proof) дают аутентичность и «доставлено», но **не** авторизацию и **не** «применено». Подписанные `Record` переиспользуем как есть (семантика цепочки/`seq`/отзыв); доставка адресно по LXMF.

### 3.2 `AdminCmd` (msgpack, в `content/fields` LXMF или теле Request)

```
v:1, id: bytes16 (random), node: bytes16, root: bytes16,
op: "policy.set" | "config.set" | "rec.deliver" | "status.get",
args: {...}, expect: u64|null, exp: u64 (unix s)
```

Актор — identity источника LXMF или identify на Link; отдельной подписи поверх не вводим (адресат входит в подписанную часть LXMF; `node` — страховка). Сообщения ≤ 4 КиБ, вложения выключены (0018 §5).

### 3.3 Обработка на ноде (порядок)

1. **Границы:** размер, версия, rate-limit на актора (`CtrlBucket`), ≤ 32 pending на actor, ≤ 256 на root; переполнение — отказ, допущенных соседей не вытесняем.
2. **Идемпотентность:** `(actor,id)` в журнале → вернуть сохранённый результат.
3. **Срок/адресат:** `exp > now` (с допуском на расхождение часов), `node == me`.
4. **Права заново** по текущему хранилищу (`rights_in` в `root`, не union); для node-local — только own-root; для `policy.set` — `ceiling(R)`. Подпись, validity, отзыв и права проверяются **при применении**, а не при отправке: отозванному админу поставленная команда не применится.
5. **Версия:** `expect` против текущей; несовпадение — `stale(current)`; если состояние уже равно желаемому — `applied` (set-подобные операции идемпотентны).
6. **Атомарный durable commit** состояния + запись журнала (`temp+fsync+rename`); хранилище вне очищаемого `lev-{role}`. Журнал живёт до `exp + 24 ч`, ограничен.
7. **Результат** (`applied | rejected(code) | stale | expired`) отправляется **после** commit: LXMF-ответом/Response. «Доставлено в PN», «доставлено», «применено» — разные состояния; UI показывает раздельно (UI-proposal §5.1).

Для `rec.deliver` ACK означает «запись принята `accept_rec` и сохранена `save_trust`» — **не** «доставлена».

### 3.4 Согласование с UI

- «Записано локально» (подпись телефоном) ≠ «применено на ноде» ≠ «доставлено» (UI-proposal §3.2, §5.1). Статус «применено» выставляется только по ACK ноды.
- `command_id` = `id`; повтор — тот же `id`; отмена — новая отменяющая команда.
- Офлайн-отзыв честно pending: пока нода не получила запись/команду, `HOST_ACCESS` у неё **действует** (UI-proposal §5.4). Отзыв доставляется повтором до ACK; идти по двум путям (gossip `T_REC` + LXMF) допустимо — идемпотентно по `seq`.
- Не блокировать dataplane: admin-обработчик в отдельной задаче; `trust`-мьютекс на короткие секции; согласования (комиссионер) — вне пути пакетов. Пакеты IP через LXMF не идут. Параметры VPN/E2E GCM/replay/no-downgrade не меняются.
- Экспорт: `status.get` ≤ 16 КиБ, без секретов/seed/PIN/профилей; адреса операторских алиасов — только счётчик; полный список — `config.get` с own-root CONFIG; выгрузка записей — scoped по общему корню.

## 4. Прикладной ACL пакетов

### 4.1 Что есть **[проверено в коде]**

- `TunState::on_link_packet` (`lib.rs:1874`): non-IPv4/`len<20` — drop; на выходе при `enforce` сверка `src` с `allowed[link]` (устанавливается `allow()` из `admit_client13`, `vpn.rs:4316`). **dst, `ihl`, длина, фрагменты и протокол не проверяются**; затем `write_tun`.
- `tun_reader`: на выходе маршрут по `dst` в `routes`.
- `client_ip` — хвост хеша identity в `/15` (`vpn.rs:726`); коллизия отвергается `address clash`.
- `knothop.nft`: `input` — ICMP accept, затем безусловный `client->node` drop для `iifname khd0`; `forward` — drops `fib daddr type local`, `@own_public_v4/v6` (W78), private ranges, IPv6; `output` — loop-guard.

### 4.2 Целевая схема: enforcement в приложении, до TUN

**Принцип.** Приложение — единственный обязательный фильтр. Оно **не полагается** на то, что «обычный интернет-путь не менялся»: без nft (или после его удаления) сам по себе пакет клиента с `dst` на собственный адрес ноды доходит до host stack, поэтому default-deny для не-интернет адресатов реализуется в приложении явно, а не наследуется от шаблона.

#### Классы адресов назначения (`dst`) и источника (`src` ответов)

| Класс | Что входит | Решение приложения |
|---|---|---|
| **H — host-owned, точные** | IPv4, назначенные ядром интерфейсам самой ноды (по inventory): собственные публичные, **собственные точные RFC1918**, **собственный сервисный адрес TUN** (`khd0`), плюс операторский публичный NAT-alias (точный /32 из валидированного списка оператора; в FIB гостя его может не быть — W78/RU) | нужен `host_ok(link)` **и** адрес ∈ `host_allow` (ниже); иначе drop |
| **D — deny always** | loopback `127/8`, `0/8`, multicast, `240/4`, broadcast, link-local `169.254/16` (если не H), любые «martian»; адреса из этого класса **никогда не публикуются** в inventory, alias-список и `host_allow` (отклоняются при валидации), права на них не дают | drop + счётчик, независимо от прав |
| **R — remote private / LAN / Docker / прочее чужое** | RFC1918, CGNAT `100.64/10`, link-local, подсети docker-мостов и контейнерные адреса, адреса других клиентов туннеля (`198.18.0.0/15`, кроме собственного сервисного адреса ноды) — всё, что **не** принадлежит самой ноде | drop + счётчик; **HOST_ACCESS не распространяется** ни на какую подсеть, даже если нода сама в ней |
| **U — unknown / unclassified** | inventory не готов/устарел/не синхронизирован (ниже), либо адрес не удалось классифицировать | fail-closed (ниже) |
| **P — публичный интернет** | остальное: публичный IPv4, не входящий в H/D/R | как сейчас: forward/exit |

`HOST_ACCESS` разрешает **только** точные адреса из `host_allow` ⊆ H, а не подсети и не весь класс H. Прикладной ACL по `dst` — не фильтр портов и не контроль listeners других приложений.

**`host_allow` (предложение дефолта, ограничение MVP).** Состав — решение владельца ноды (node-local CONFIG, own-root). **Дефолт предлагается узким:** публичные адреса из inventory и операторский публичный alias. Собственные RFC1918 и сервисный адрес TUN остаются в классе H (то есть тоже защищены от клиентов без права и **не** уходят в R/P), но в `host_allow` попадают только по явной записи владельца с точным адресом. Это **ограниченное предложение MVP «public-by-default»**, а не отказ от того, что сервисы могут слушать на адресе TUN или на приватном адресе ноды: механизм допускает их как точные записи, дефолт лишь консервативен. Enforcement без nft при этом **отказывает непубличным собственным адресам без прав и без записи в `host_allow`**.

#### Inventory адресов ноды: готовность и fail-closed

- **Bootstrap:** inventory (адреса интерфейсов ядра + операторский alias-список) строится **до** открытия TUN и допуска клиентских data-Link. Нет готового inventory — клиентский exit-трафик не принимается (drop, счётчик `inventory_unsynced`), `eff_host.inventory = "unsynced"`.
- **Refresh:** подписка на изменения адресов ядра (netlink) + периодическая полная сверка (≈5 с). Потеря/переполнение подписки, ошибка чтения, возраст последней успешной сверки > порога → состояние `unsynced`: **host_ok не действует ни у кого**, а клиентский exit-трафик приостанавливается до ресинхронизации (кратковременная потеря доступности — осознанная цена fail-closed; измеряется в overhead-тесте).
- **Исключения из авто-inventory:** адреса интерфейсов контейнерных мостов (`docker0`, `br-*`, `veth*`, CNI) в H автоматически не попадают; владелец может внести такой точный адрес в `host_allow` явно. Изоляция Docker **не протестирована**.
- Ошибка классификации = класс U, не P: неклассифицируемый `dst` не пересылается как «интернет».
- Остаточное окно между появлением нового локального адреса и обработкой события — ограничено задержкой события/сверки; это честное ограничение, закрываемое только синхронной проверкой ядра на каждый пакет (не предлагается из-за стоимости).

#### Проверки на входе (`on_link_packet`, ветка `is_exit && enforce`, после проверки `src`)

1. **Версия/форма:** `version == 4`, `ihl ≥ 5`, `ihl*4 ≤ len`, `total_len == len` (или явно `≤ len` с обрезкой — выбрать один вариант и покрыть тестом), TTL > 0; иначе drop + `malformed`.
2. **IPv6 и прочие версии:** `version != 4` — **reject (drop + счётчик `non_v4`)**, не bypass и не «пропуск мимо ACL». VPN IPv6 не поддерживает; `HOST_ACCESS` v4-only, `status` говорит об этом явно. IPv6-адреса ноды в inventory не публикуются.
3. **Классификация `dst`:** D, R, U → drop; P → прежний путь; H → дальше.
4. **Для H:** нужен `host_ok(link)` и `dst ∈ host_allow`; proto ∈ {tcp, udp, icmp}, остальное (GRE/IPIP/ESP/SCTP) — drop; IP-options — drop; **фрагменты (`MF` или offset ≠ 0) — drop** (в MVP: без сборки; ограничение — большие UDP-датаграммы к сервисам не пройдут; сборка с лимитами — позже вместе с port-ACL).
5. **Служебный ICMP TUN:** единственное исключение без `host_ok` — ICMP echo-request на собственный **сервисный адрес TUN** ноды (health/probe туннеля), с rate-limit; ICMP на прочие адреса H — как любой трафик H, требует права. **Успешный health/probe не равен разрешению:** ответ на echo не свидетельствует о `HOST_ACCESS`, а активная проба админа (положительный контроль доставки) — отдельный диагностический вызов, не источник прав.

#### Проверки ответов (`tun_reader`, направление нода → клиент), симметрично

1. `version == 4`, `ihl`/`len` корректны; не v4 — drop.
2. `dst` — адрес клиента из `allowed`, получатель определяется однозначно; иначе drop.
3. Классификация `src`: D, R и U — drop; P — как сейчас; H — нужен `host_ok` **того Link, которому адресован пакет**, proto/options/фрагменты — как на входе; исключение — echo-reply с сервисного адреса TUN на разрешённый выше echo-request.
4. Ответ сервиса клиенту без права не уходит, даже если пакет в хост был доставлен раньше (право отозвано): проверка делается на каждый пакет в обе стороны.

`host_ok(link)` — атрибут записи клиента (`allowed: HashMap<LinkId,u32>` → структура с `ip` и `host_ok`), пересчитывается в `enforce_rights` (на каждое принятие записи/политики) **и периодическим тиком** (≈2 с) для истечения `Policy`; при `inventory != ready` он принудительно false. **Revoke активного потока:** со следующего пакета в обе стороны; Link VPN при этом остаётся (UI-proposal формулирует «потоки к службам будут закрыты» — по сути так, но не закрытием Link).

**Источники `host_allow`/inventory.** (а) адреса ядра — из inventory (метки интерфейсов); (б) операторские алиасы — литеральные публичные IPv4 (≤ 64) из `own-endpoints.conf` (root 0600, недоступен `knothopd`) — приложению нужна валидированная копия в state, которую публикует hostfix/оператор (loopback/D/R в ней отклоняются при загрузке); (в) явные записи владельца (точные адреса, включая собственные RFC1918 и сервисный адрес TUN). Loopback и «target localhost» в гостевой FIB — **разные** вещи: loopback из туннеля — martian, класс D, и в `host_allow` не входит; публичный NAT-IP оператора, которого нет в FIB гостя (W78), — только из доверенного списка оператора; неизвестный NAT-alias приложение обнаружить не может (остаётся классом P — **остаточный риск**, закрывается только списком оператора и пробой).

**Link identity / source IP.** Право берётся по identity `Role::Client{id}`, зафиксированной при допуске; IP привязан к Link через `allowed`. Два риска ниже (§5.2): повторный identify до допуска и коллизии IP.

**Никакого контроля listeners других приложений:** ACL работает по dst-адресу/протоколу и identity, порты и процессы хоста не трогает и не закрывает глобально (SSH, firewall других приложений не затрагиваются).

### 4.3 nft: defense in depth, не backend прав

Требования владельца: nft — не универсальная внешняя зависимость; функция **не** условна к его наличию, динамических sets/`CAP_NET_ADMIN` на каждый grant нет.

- **Правила прав живут в приложении.** nft-слой, если он есть, статичен: после одной раскатки шаблона не меняется при grant/revoke и не знает identity.
- Статический defense-in-depth в рамках уже разрешённого host path (по точным адресам `host_allow`, только tcp/udp, только `iifname khd0`): сужает последствия ошибки ACL приложения, но **не** различает identities — различает только приложение.
- Ноды без nft: функция работает на ACL приложения. Классы D/R/U (§4.2) в приложении — **обязательная часть S2**, а не опция: default-deny для private/special/unknown не может зависеть от того, есть ли nft. На узлах с шаблоном это дублирует `client->internal` (поведение клиента не меняется), на узлах без него — единственная защита. Тезис «интернет-путь не менялся» реализацией default-изоляции не считается.
- Опциональный адаптер (не default, не permission backend): динамический набор `host_access_v4` с таймаутом для узлов, где владелец захочет третий слой; отдельное разрешение на привилегию, **не** часть MVP.
- Что **нельзя** обещать: accept в нашей таблице не отменяет drop в чужих base chains (`KnotHop`, iptables/ufw): если чужой firewall режет источник `198.18.x`, доставка не произойдёт; достижимы сервисы, которые нода публикует на глобальный адрес и которые чужие правила пускают.

### 4.4 Действующий INPUT drop и честный технический блокер

**Факт [проверено в коде]:** при `iifname khd0` сейчас безусловно действует `client->node` drop (кроме ICMP). Пакет, прошедший app ACL и записанный в TUN, на хосте с этим шаблоном **будет отброшен** в INPUT (для адресов, локальных в FIB — FI-случай) или в `forward` `own_public`/`local` drops (для NAT-алиасов — RU-случай). Следовательно:

- app ACL сам по себе **не доставит** пакет в host stack на узле с текущим шаблоном. Это не вопрос «nft как внешней зависимости» — это собственное статическое правило пилота.
- Это закрывается **одноразовым статическим** изменением шаблона: accept для `iifname khd0 ip daddr @host_allow_static meta l4proto {tcp,udp}` (набор генерирует hostfix из тех же точных адресов `host_allow`; меняется только когда владелец меняет этот список, не на grant/revoke) перед `client->node` и перед `client->own-endpoint-*` drops. Без saddr-set, без обновлений на grant; per-identity решает приложение (клиент без права до TUN не доходит). Это firewall persist по AGENTS — **отдельное разрешение** на раскатку; в лаборатории проверяется без него.
- Альтернативы (каждая со своей ценой): (а) узлы без nft/без `client->node` drop — работают сразу; (б) явно отключить `client->node` на конкретном узле — теряется защита для остальных путей; (в) TCP/UDP-прокси в приложении — **запрещено архитектурой** (AGENTS: не заменять VPN TCP-прокси; единица данных — IP-пакет).
- Если на конкретном узле доставка заблокирована чужим firewall, нода не должна «обещать»: capability `host_access` отражает наличие app ACL и готовый inventory (§4.2); **доставку** подтверждает активная проба админом (положительный контроль с телефона), а не nft-readiness. UI показывает «выдано, доставка не подтверждена».

### 4.5 Что обещаем и чего нет

Обещаем: клиент с `HOST_ACCESS` в таком ACL достигает tcp/udp-сервисов самой ноды **только на точных адресах `host_allow`** (в дефолтном предложении MVP — публичные и операторский alias; собственные RFC1918/TUN — по явной записи владельца), если не режет чужой firewall. Без права или вне `host_allow` собственные адреса (в т.ч. непубличные) отбрасываются приложением; обычный публичный интернет-трафик клиента идёт прежним путём. **Не** обещаем: loopback-only (класс D, всегда deny), Docker published ports (после DNAT цель частная → остаётся под `client->internal`; **изоляция Docker не протестирована**), LAN, IPv6, неизвестные NAT-алиасы, per-port политику, «все Linux-сервисы».

### 5.3 Тест-план

- **unit (`trust.rs`):** parse/roundtrip бита 64; reject 128; `ALL==63`; старые записи ≤63 без изменений; `PRESET_ADMIN` без бита 64; root authority = `KNOWN`; `host_in` по корню: нет OR (регресс на `rights()`), чужой self-root ничего не даёт, непринятый якорь, якорь без `host_trust`; multi-root: отзыв в X оставляет вклад Y; own-root-запись (включая `rights=0`) перекрывает network; `local_deny`; просрочка политики; `ceiling`; самовыдача `CONFIG` невозможна и `HOST_ACCESS` не добавляет `CONFIG`; запись с неизвестным битом отвергается целиком (не маскируется); `scope_ok`: own-root — да, root-wide `Record` v1 сети с битом 64 — игнорируется для `host_in`, network без scoped-доказательства — отказ, подмены root-wide нет; глубина/квоты; mixed-version (старая нода отбрасывает запись 64 целиком).
- **unit/integration (`vpn.rs`/`admin.rs`):** replay `id`, `exp`, чужой `node`, отозванный актор в очереди, `stale`, крах между commit и ACK, лимиты, scoped export, ACK = durable commit (после рестарта состояние есть), `rec.deliver` по LXMF, один и тот же `AdminCmd` по двум носителям.
- **packet lab (изолированная netns, не публичная RNS):** с/без права; spoof src; фрагменты (оба направления); IP-options; malformed ihl/len/version; GRE/IPIP; IPv6 (reject, не bypass); ICMP (служебный echo на TUN-адрес без права, прочие H — с правом; probe ≠ право); dst loopback/RFC1918/CGNAT/link-local/docker/другие клиенты — deny без nft; собственный RFC1918 и TUN-адрес без записи в `host_allow` — deny даже с правом; inventory bootstrap/потеря netlink/новый локальный адрес — fail-closed; revoke во время потока (обе стороны); коллизия IP; повторный identify; положительный интернет-контроль (обычный публичный egress работает); сценарии узла без nft и с текущим шаблоном (ожидаемый drop в INPUT) и со статическим exception; чужой INPUT drop; alias из списка vs неизвестный NAT; Docker-проба (пока не выполнялась).
- **overhead (в `docs/experiments-log.md`, с объёмом/условиями):** CPU/PPS/память до/после для обычного трафика (один hash-lookup на пакет в обе стороны), потери/RTT/джиттер; fastpath ядра не менять; LXMF на пакетах нет.
- **Android UX:** `eff_host` по (я, target), причины disabled, офлайн-очередь с раздельными состояниями, стале-версия, отзыв во время офлайна; без лабораторных интентов.

## 6. Актуальные факты изоляции (W78, без адресов)

- **FI:** адрес из старого pcap-target (FI-02) — **retired**, он не относится к новой FI; результаты FI-02/FI-05 не используются как факт про новую ноду. Для **новой FI** собственный текущий адрес локален в FIB (route `local` для phone-TUN source, `iif khd0`), проба известных listeners 22/47001/443 дала SYN без SYN-ACK, счётчик INPUT `client->node` вырос на 6: блокировка штатным INPUT **подтверждена**, hairpin-экспозиции не найдено. Владелец подтвердил trusted текущий IP новой FI, pinned SSH проходит — повторно не переспрашиваем. IPv6 для FI не публиковался (DNS AAAA нет) — не приписывается.
- **RU:** воспроизведён current own-endpoint gap (route в WAN, SYN-ACK на 22/47001/443), применён runtime-only фикс (`own_public_*` sets + три forward drops в `inet knothop`), после фикса 0 SYN-ACK, drop-счётчик +6, положительный egress-контроль прошёл. **Persist не выполнялся**, `own-endpoints.conf` на серверы не provisioned, локальный шаблон/`node-hostfix.sh` не staged; правила могут пропасть при reboot/reapply.
- **Не проверено:** изоляция Docker (probe не выполнялся — подходящего контейнера не нашли); IPv6 live-probe; остальные 6 узлов.
- **Следствие для `HOST_ACCESS`:** на FI доставка к собственному адресу идёт через INPUT (`client->node`), на RU — через forward/hairpin (`own_public` drop); для каждой схемы нужен свой исход статического исключения (§4.4) и своя проба. До закрытия W78 persist/rollout расширять доступ внутрь нод нельзя.

## 7. Что осталось неопределённым и решения владельца

**Технические unknowns (не вопросы владельцу):**

1. Как раскатывать бит 64 в смешанной сети: старые ноды отбрасывают запись целиком; нужен порядок «ноды сначала» + coverage check; отдельный механизм (вторая запись/другой тип) не разведён.
2. Реализация и семантика scoped-доказательства (`EnrollRec`, 0019, нет в коде): без неё network-grant `HOST_ACCESS` на конкретную ноду **отключён** (в MVP только own-root), а не root-wide.
3. Окно повторного identify до допуска и прочие читатели `get_remote_identity` — подтвердить/опровергнуть тестом.
4. Поведение чужих firewall (`KnotHop`, iptables) на источник `198.18.x` по каждому узлу и hairpin-путь RU — только пробой.
5. Изоляция Docker, IPv6, остальные 6 узлов — не измерены.
6. Inventory адресов (§4.2): надёжность netlink-подписки, период сверки, цена паузы exit-трафика в `unsynced`, остаточное окно появления нового адреса; неизвестный NAT-alias — только список оператора.
7. Размер overhead от классификации `dst`/`src` на каждый пакет и поведение при фрагментированном UDP к сервисам (MVP их отбрасывает) — измерить.

**Новые policy choices (предложения, решение нужно только по ним; принятые направления не переспрашиваются):**

1. **Политика `host_trust` по умолчанию:** кому нода доверяет выдачу `HOST_ACCESS` — (а) только own-root, (б) own-root + явно перечисленные принятые якоря (рекомендую), (в) любой принятый якорь. Мульти-root поддерживается во всех вариантах; различается дефолт.
2. **`cap` приглашения Invite v4:** `0x07`, либо `0x47` с coverage check на каждой ноде (§2.6), либо отдельная выдача после зачисления. Бит по умолчанию не блокируем.
3. **Разделение CONFIG по классам и потолок** `ceiling(R)` (§2.3): принять ли, что network CONFIG действует только внутри потолка, заданного владельцем ноды, и `HOST_ACCESS`-offer в R ограничен им.
4. **`local_deny`:** принять ли как явный высший приоритет (§2.2) и как его формализовать (CLI/подписанная запись).
5. **Частичное понижение** (запись `new ⊂ old`) — разрешить одним `REMOVE` или оставить `ADD` (существующее поведение `issue`).
6. **Дефолт `host_allow`** (§4.2): предложено публичные адреса + операторский alias, собственные RFC1918/адрес TUN — только по явной записи владельца. Это ограничение MVP, не отказ от приватных/TUN-адресов.

Не переспрашиваем принятое: keepalive 25 с, pin 48 ч, пустой `app_data`, 0019 (общий pin 24 Б, scoped-записи, LXMF-ACK закрывает pin), отказ от `ADMIN_CONFIRM` и emoji, направление «ACL в приложении, nft — defense in depth», trusted FI IP.
